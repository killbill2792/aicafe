## Capabilities and schemas

All requests use strict Zod input validation, literal `version: 1`, and reject unknown fields such as `businessId`, client-supplied employee records, costs, wages or SQL. Call `executeOliviaReadCapability(raw: unknown)` **only from an authenticated trusted server integration**. PR4A deliberately adds no endpoint, model tool, registry entry, or UI integration.

| Capability | Accepted fields | Trusted result | Semantics |
| --- | --- | --- | --- |
| `olivia.availability.read` | `version: 1`; optional `employeeId: UUID` | owner-café roster ID/name/active, confirmed and unconfirmed recurring rules, date exceptions including approved leave/unavailable, hour limits, preference windows, qualifications, compensation provenance and available confirmation/update timestamps | Per-worker `state: confirmed / unconfirmed / missing / unavailable` summarizes saved **evidence**, not each day’s eligibility. Inactive employees and negative-only confirmed availability are labeled `unavailable`. Confirmed leave overrides a recurring window on its date via PR2; no positive availability is invented. Missing wages are not verified zero. |
| `olivia.schedule.preview` | `version: 1`, `week: Monday YYYY-MM-DD`; optional `options.objective` (cash, owner_time, balanced), `expectedRevision` (0–500), `expectedSourceDigest` (SHA-256 hex) | PR2 `PlannerResult` with all scenarios, optional selected objective, assignments, exact UTC uncovered intervals, cost states/cents, owner minutes, warnings, blockers, source digest and preview head | **Proposal only**, no draft saved and no publication. Existing PR3 trusted inputs cap solver resources (`maxNodes: 12000`, `beamWidth: 24`). This contract does **not** accept arbitrary solver budgets, staffing or hourly sales. Manual owner-entered coverage works without POS. |
| `olivia.schedule.history.read` | `version: 1`, `week` | immutable revision listing (draft/approved/published/superseded), current head and official published revision pointer | No revision inferred from draft status. A published pointer must resolve to a published record. Revision readback independently re-reads PR3's owner-scoped history and checks complete immutable versions, the **unique** official published status, the requested row's ID/status, and unchanged head/published pointers (otherwise `revision_conflict`). |
| `olivia.schedule.revision.read` | `version: 1`, `week`, `revisionId: UUID` | existing version/`revisionStatus`, source digest and validated persisted assignments matched against the stored scenario, plus head/published pointers | Read-only; reject malformed, missing, or mismatching persisted shifts. Draft is not approved; approved is not published. |

**Response contract:** `ok: true, version: 1, status: "ok", capability, source, …` or `ok: false, version: 1, status: "error", capability, error: { code, retryable, message }`. When the trusted PR3 preview fails with `missing_inputs`, the response additionally carries schema-validated `blockers` (`no_location`, `no_coverage`, `conflicting_limits` and optional employee name); malformed/untrusted blocker details fail closed. Source metadata identifies the authenticated café and labels a multi-query source/preview `provisional`. All successful responses are parsed against strict output schemas. Safe errors are bounded and contain no SQL/provider details.

**Resource limits:** Missing-wage IDs may be represented for up to 2,000 provisional PR2 shifts before the adapter classifies over-200-shift previews as capacity; IDs must be unique and refer to actually assigned workers. 500 people per availability read, 5,000 entries per record class, 500 revisions, 200 shifts per persisted revision. PR3 warning notices are preserved through its maximum 20,000-row scanned-staff bound (at most 3 per worker plus six global notices), instead of dropping/rejecting valid plans with more than 100 actionable notices. All currency cents—including signed scenario comparison differences—must be JavaScript safe integers; unsafe aggregates fail closed as invalid stored/planner evidence. Each scenario permits up to 20,000 exact uncovered intervals (including valid 5-minute coverage grids). Larger structurally valid planner results produce the explicit `capacity_exceeded` response **after relaxed-capacity schema validation**, never misleading `invalid_record` or silent gap truncation; this is an Olivia capability transport bound, not a PR2 optimizer change. The same distinction applies to provisional PR2 preview results with more than **200 shifts** (PR3's persistable draft maximum) or more than 100 optimizer warnings: they are not misclassified as corrupt evidence; no oversized drafts are saved. **All fields and elements of a too-large plan are validated using a relaxed-cardinality schema before returning `capacity_exceeded`.** Malformed workers, intervals, costs or comparisons remain `invalid_record` even in oversized scenarios. Exact row counts guard employee and persisted-assignment reads against PostgREST caps; revision history must contain every immutable version from 1 through the current head. Excess/partial source data fail rather than being silently truncated. The underlying PR1 complete foundation reader also has its own pagination and consistency limits. Version increments require a new reviewed contract, not a silent shape change.

## Authorization, provenance and failure policy

1. Owner identity and selected café are resolved using the existing trusted server membership boundary, not model/client values. Manager, employee, demo, foreign tenant and forged-employee access must fail closed. The adapter rechecks owner/café context **immediately after every awaited staff, foundation, preview, history, revision and assignment read—before interpreting success, failures, setup blockers, existence, counts or source digests** to avoid leaking details from a café switched mid-request.
2. All employee lookups and revision-assignment reads are restricted by trusted `business_id`. Raw foundation record tenant IDs must match the authenticated café **before** projection. Unknown IDs return `not_found` without revealing whether another café has that employee or revision.
3. Raw stored source rows are projected through the Olivia field schemas. Confirmation flags are never promoted; confirmed negative leave remains negative evidence. A worker whose only stored availability is unconfirmed is not automatically eligible.
4. Preview never writes. Do not equate `unknown` cash costs with `0`; the optimizer already models missing qualifications, split/overnight/DST, cross-location overlap, protected published shifts and exact gaps. It does not invent POS data, labor rules or owner-worker identity.
5. Preview digest and revision options can detect stale client state. Before reporting a stale-token conflict, the adapter checks token shape and source correctness, binds the preview to the requested seven-day Monday horizon, requires PR2 canonical unique objective order and a consistent best-feasibility witness, verifies every shift/gap/missing-wage ID against trusted worker and location maps, and cross-checks claimed comparisons against actual scenario cents/minutes. All scenario owner-minute totals must match their cost evidence. PR3 publication still **independently reloads sources, validates the legal profile and assignments and enforces transactional CAS/source tokens**. A PR4A preview is *not* an authority to publish.
6. Malformed domain responses, inconsistent DB revisions, partial reads, missing providers and exceptions fail with stable error codes. No client- or AI-generated sentence is accepted as evidence an owner action occurred.

## Future owner-action intents — not executable

`futureOliviaOwnerIntentSchemas` declares **edit**, **approve** and **publish** payload shapes for a later review. These are **not** part of `oliviaReadRequestSchema`; the PR4A executor rejects them. In PR4B, only explicitly authenticated owner-confirmed actions may call the existing `saveOliviaEditedDraft` / `transitionOliviaPlan` boundaries with canonical reloaded source, revision CAS, legal checks, idempotency and persisted read-back. No LLM response, generalized capability caller or manager/employee may approve/publish. There is no new publication pathway, external worker messaging, payroll write, or acceptance signal.
