# Luna assignment execution and continuation

## Decision

Keep the assignment, its authority, and its outcome in Supabase. Run the model and registered tools under a fenced worker claim. A claim can end while the assignment stays pending. Each successor uses the same run, original instructions, accepted corrections, and saved work. Use OpenAI's stateless Responses items as the model's continuation. Keep the provider request at `store: false`, as the owner directed. The existing worker remains the wake and recovery path for admitted work.

The execution model is one autonomous operator per business. A browser request, scheduled occurrence, or delegated assignment gives the same engine work to do. The owner can go offline. Each assignment retains its actor, permitted audience, source, outcome and return destination. A parent waiting on a child should release its claim and wake once from the durably recorded child result. A scheduled occurrence should retain its routine revision and due instant through recovery. The pilot branch pins saved routine occurrences to an engine and uses the same provider and tool loop. Parent and child execution still needs integration and unattended product acceptance before rollout. [Approved runtime and operating contract](luna-rebuild-handoff.md)

## Where the restrictions came from

| Path | Current behavior and consequence |
| --- | --- |
| Legacy bounded agent | The older policy has a 60-second ceiling, five or seven work model calls, one final call without tools, and eight or 24 tool calls. The original worker also bounds its chain of follow-up turns. Paid acceptance has explicitly smaller limits. |
| Legacy production research | The version 2 worker already uses an unrestricted research policy, a fenced execution deadline and a private continuation checkpoint. The research loop carries completed Responses items and tool results into another claim. A response interrupted before settlement can still lose in-flight progress. |
| Replacement Luna | The pilot uses a 55-second worker signal under a 60-second claim. The cron route itself allows 120 seconds and the browser route allows 150 seconds. The replacement copied the existing model and tool caps into its persisted transcript counters. That prematurely withdrew tools and could end the assignment even though PostgreSQL already budgets version 2 requests per claim. The pilot's prior technical yield covered only late steering. |
| Provider capacity | The existing per-request output cap is 1,200 or 8,192 depending on the model and verified database capability. The provider reservation also bounds request size and aggregate claim usage. A completed client-side tool result and its authorization lineage need to remain recoverable if the model context is later compacted. |

## Runtime and safeguards

The existing continuation row is keyed by `run_id` in `supervisor_research_continuations`. The lease and checkpoint sequence guard writes. OpenAI supplies the response ID, output item types, encrypted completed reasoning, function call name, call ID and arguments, assistant output text, terminal status and measured usage when available. Save only replayable output under the existing private checkpoint. Use a distinct partial provider receipt to prevent the result publisher from accepting an interrupted response. Pair each completed function call with its saved result before resuming. Retain the existing provider attempt accounting. A stream cut off before terminal usage keeps its conservative attempted reservation. A fresh call still needs a new reservation. Use the normal authorization, tenant, steering and publication fences across claims. [Stateless Responses continuation](https://developers.openai.com/api/docs/guides/conversation-state) · [Encrypted reasoning replay](https://developers.openai.com/cookbook/examples/responses_api/reasoning_items)

A worker deadline with saved data and an exhausted claim allowance both release the claim using the existing technical yield. The true owner quota still denies new provider spend. An uncertain effect still needs a verified effect receipt or reconciliation. Cancellation must prevent fresh tool execution or publication. The replacement's ordinary tools remain available after a fresh claim so research depth follows the task and evidence.

A foreground request that outlasts the worker before emitting a replayable item still lacks a resume point. The next infrastructure slice is to exercise a longer Vercel worker invocation against a no-output provider delay, retain lease fencing and use the same Postgres run and reservation. That requires reviewing the protected pilot entry revisions on the current base. Native stateless compaction can reduce long-context costs once its interaction with saved tool receipts and source and egress checks is verified. An unattended release needs combined evidence for real long-running responses, schedule admission, parent and child recovery, revocation, and approved effects. [Native compaction](https://developers.openai.com/api/docs/guides/compaction)
