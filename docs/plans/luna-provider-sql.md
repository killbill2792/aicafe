# Luna read-only provider SQL and external-data review

## First delivery

Give each replacement workforce assignment the existing `describe_database`, `run_sql` and `calculate` contracts. The server takes café and owner from the claimed run, passes the single model-authored statement through the existing restricted PostgreSQL connection, and records the returned rows or error under the existing run and tool-call receipt. A recovered worker uses the stored result. The publication transaction remains the authority on whether newer owner input requires another model response.

The model can inspect original provider fields in `external_records.payload`. The archive identifies the café, provider, account, resource and stable provider key. Source metadata supplies the observation date, origin and coverage. Revisions record changes and, for new deltas, whether a key was present before and after. Verified relationships and authority metadata help identify overlapping records. Missing permission, a failed collection, absent fields, explicit null and a recorded zero have distinct meanings. The audit will check those distinctions before any data-path retirement.

## Acceptance

Use original Toast order and payment payloads from a disposable two-café fixture. Ask the replacement to discover the sources, reconcile accepted net sales with available processing fees, and identify an order whose fees remain unknown. Independently check the cents, source identities and coverage. Verify that the scoped executor returns no rows for the foreign café and rejects writes, and that neither request changes persistent data. Interrupt the worker after a SQL result is saved, recover with a new lease, and confirm the result is reused. Add a late owner correction after a draft response is saved and verify the only published answer reflects it.

Employee chat and scheduled admission need the same run and rollback semantics. Test engine pins, independent due dispatch, existing history, and two-café isolation before fresh live acceptance and first-café activation.

## External-data architecture at `747db6df`

Apply the current migrations to a disposable database, inspect `pg_class`, `pg_rewrite`, `pg_depend`, and `pg_get_viewdef`, then trace SQL routines and repository callers. View dependencies below come from the migrated catalog. Direct and indirect consumers also include RPC bodies, writes, triggers, and runtime SQL whose relation names are not constrained to static imports. This is a source and migrated-schema inventory. Production coverage figures come from the linked audits.

**Provider evidence.** [PR #593](https://github.com/killbill2792/aicafe/pull/593) introduced one shared archive, with the existing Toast raw tables attached as physical partitions. `external_records` holds the latest permitted JSON per scoped object. `external_record_changes` preserves observed changes in place, including exact paths and presence flags where captured. `external_resources`, `external_sync_checkpoints`, and `external_observation_members` record permission, paging, freshness and collection membership. A point payment receipt and a completed payment-day listing establish different evidence. `external_identifiers` and `external_record_links` preserve provider aliases, app linkages and their provenance. The three identity views express current identifiers, candidate relationships, and selected authority for overlapping evidence. Candidate relationships alone cannot establish a join. Historical records may lack a modern observation receipt. [PR #601](https://github.com/killbill2792/aicafe/pull/601) attributed 979 records and 7,777 revisions without changing their JSON. It still recorded 117 rows and 2,904 revisions without sufficient scope evidence for adoption.

**Agent access.** Native SQL already uses the restricted transport and café-scoped executor. The replacement now discovers resource names, original JSON shapes, aliases, links and history through that same path. The model decides its joins and analysis. App-owned facts and existing audited financial values remain queryable evidence where useful. There is no canonical-view prerequisite and no new analytical SQL interface. Earlier `ai_query_view` and `ai_toast_fields` RPCs have already been dropped. The separate `u3_research` catalog retains signed-scope compatibility definitions and acceptance dependencies. Its eventual retirement requires tracing the U3 callers and receipts independently of these application views.

### PR #602

[PR #602](https://github.com/killbill2792/aicafe/pull/602) replaced one fee-estimate reader over legacy `orders` with the existing `cv_orders` application read, using stable pages per business day. It added no object, view expansion, table or aggregate strategy. This keeps the fee estimate and daily rollup on the same order identity and accepted money, and retains actual fee precedence. The PR records parity for 12,653 accepted Toast orders, 17,793 non-voided lines, and 97 selected fee days. It also found 557 historical lines without a local menu item link. The first set supports changing the reader. The last finding rules out assuming every legacy line's relationship is recoverable from source names or prices.

### Simplest verified direction

Use the scoped archive, provenance and native app state as the foundation. Let models choose SQL against original data and choose shared business calculations where a named app result matters. Keep deterministic app contracts that still have consumers, fallbacks or coverage rules. Stop introducing precomputed interpretations for research. Preserve financial correctness by tracing authority and retaining the app semantics behind a named metric. Redundant copied values should disappear incrementally, beginning where the archive has matching identity, version and complete coverage. Keep one shared app derivation where multiple screens consume the same number. Keep a cache only after measuring need and documenting invalidation and historical behavior.

Before a physical retirement, run old and proposed reads over full available history and compare row identities, values, status, source and as-of. Include an unlinked line, missing original, manual edit, split payment, provider revocation, two cafés, and rollback. Measure the existing and new queries on the same workload. Writer cutovers and physical retirement need their own evidence. The SQL and recovery patch needs no schema change to deliver original-source access.
