# Luna rebuild

The [implementation handoff](luna-rebuild-handoff.md) records the agent workflows, architectural decisions, test evidence and implementation order. It supersedes the early approach of wiring the conversation surface before proving the replacement harness.

Luna is the operator an owner can delegate a shift to. An owner or employee should be able to return to the same conversation after closing a browser, see what actually happened, correct the assignment, and retrieve its output. A reminder is complete when its delivery has a receipt. A research request can complete in the current conversation without creating a routine.

## Execution and ownership

Base for the initial design is main at 28622880. Draft PR #593 at d03e1273 owns external ingestion, archive keys, source grants and research data discovery. Its resource identity is business, provider, source account and resource. An unknown grant, an empty result and an unsuccessful collection are distinct observations. Luna should consume the scoped research functions and their coverage metadata. Recheck the merged contract, permission revocation and two-business isolation before integration. This branch can independently develop conversation, scheduling and presentation behavior. Do not bring the archive migrations into this branch.

Owner or employee message → authenticate actor and tenant → admit one logical run → claim a due step → select authorized tools → persist the result → deliver and record a receipt.

| Source | Durable identity and fields | Readers and constraints |
| --- | --- | --- |
| Existing owner chat | Business, owner, thread and original message ID; original receipt time, attachments and answers | Conversation service, worker and browser resume from stored IDs. Employee conversations keep their own permission scope. |
| Time, routine or business event | Business, schedule ID and occurrence; due instant in UTC, IANA zone, recurrence or source event identity, delivery destination | Existing one-minute worker claims due occurrences independently of POS refresh. Preserve original occurrence through retries and DST. |
| Execution | Existing run/step, engine version pinned at admission, lease token, retry time, effect checkpoint and attempt receipt | Worker renews the lease and checks current authority before dispatch. Browser stop and retry address a persisted run. An uncertain external send requires reconciliation. |
| Business knowledge | Source grant, observation version, tenant notes, corrections and provenance | Tenant-scoped tools resolve records on demand through the business layer. A revoked permission invalidates evidence on resume. |
| Document | Stable document ID, business, authorized thread, immutable version, predecessor and private Storage object | Save before reporting success. Readers verify permission on every read. Concurrent edits compare expected predecessor and retain both authors' work. |
| Owner decisions and staff messages | Existing proposal, recipient identity, approved revision, effect hash and receipt | Recheck authority at delivery. A correction to a document or chat message cannot authorize a business action. |

Assign one engine to each admitted run, including work created by a routine. Rollback changes future admissions. Drain already claimed work under its recorded engine and reconcile uncertain effects before enabling a successor. Keep legacy identifiers, access rules and readable content throughout. An environment flag alone cannot fence workers.

## Research and validation

The capability matrix will distinguish physical application behavior, deterministic checks and authorized provider acceptance. Live provider execution, production migration, deployment and destructive retirement require separate authorization. The new route stays opt-in until that evidence exists.

## Architecture decision and upstream evidence

Use Assistant UI's React primitives and its first-party AG-UI adapter for the owner conversation. A Luna HTTP endpoint admits work and projects authenticated durable state into AG-UI events. The Postgres worker owns execution even when every browser is closed. Supply JSON Render presentations through the same conversation, with the existing private attachment store for files. There is one run, one conversation history and one place to authorize effects. The tenant rollout chooses the engine when work is admitted. Owner approval covers this local schema design.

**Where the evidence lives.** Extend `supervisor_routines` and `supervisor_routine_occurrences` for trigger activation and the scheduled, event or test identity. The current daily occurrence key is (business, routine, local date). Preserve those historical rows. For new work, enforce uniqueness per business and routine on the logical due UTC instant, verified source-account/event ID, or manual request ID, and store the admitted instruction revision alongside it. Editing a schedule must never create a second attempt at an already admitted effect. Use `supervisor_runs` and `supervisor_run_steps` for parent and child IDs, checkpoints, waiting and terminal state. `supervisor_investigations` carries observation evidence. Route notices through the existing priority-notice writer to `operating_tasks` and `ai_messages`. Proposal revision and effect hash stay in `supervisor_proposals`, with confirmation in `supervisor_effect_attempts`. Source coverage, zone, recipient membership and connected accounts vary by business and are resolved at execution.

**First implementation proof.** Seed two businesses in a disposable migrated database. Admit a café owner's unscripted request and a scheduled assignment with refresh disabled. Both must reach the same worker and use an authorized tool under their original business and actor. Race two claims, interrupt after storing the result and before delivery, then reconnect. Inspect the stored input IDs, engine, occurrence, attempts, result and delivery receipt. Expect one result per logical assignment, one verified delivery per destination and zero reads or deliveries in the other business. Mark a missing connector, ambiguous external send or budget stop with its actual outcome. Register the matching executable scenario in the existing acceptance suite before integrating the slice.

### Model execution

The provider boundary accepts the authenticated conversation, clock, scoped tool descriptors and durable checkpoints. It returns text or structured content, tool requests, usage and finish state. On resume, resolve the current tool and current grant again. A provider item ID may help continue a turn. The database run and effect key remain independently recoverable. Existing calculation and action tools already enforce valuable business semantics. Keep those services callable from the new loop and preserve their structured errors.
