## Proposed one-path architecture
1. In the existing authorized Toast order archive, use only explicitly verified payment cardholder name leaves on nonvoid eligible payments, extracting before the read projection strips card containers. No parent JSON opening and no broad guard relaxation. Ingestion sanitize names and untrusted content, reject placeholder/blank/control/credential-shaped or malformed names; allow Unicode, spaces, hyphens, apostrophes, preserve original safe display and normalize whitespace/case consistently. A verified full cardholder name takes priority over server-entered check tabName; a partial cardholder name stays partial (no invented first/last; choose fallback if full name unavailable per owner priority, retain provenance). For a single unstructured name do not pretend surname parsing is certain. Explicit Toast customer names separate provenance, never silently label as server-entered until verified. Conflicting eligible payer names on a split check -> ambiguous payer evidence; no deterministic arbitrary first/last payer. Cash without a card uses server/barista name if present; otherwise unknown.
2. Identity is NOT display name. Only provider-confirmed stable non-payment customer GUID or loyalty account identifier with verified semantics and vendor namespace can link visits. Tenant + source namespace (+ provider restaurant if identifiers location-local) + stable identifier; explicit same-person source link only, conflict remains ambiguous. Payment GUID is a transaction, not a person; no card number, tokens, network, last4, fingerprints, card ID hash, email/phone or fuzzy name matching for linkage. Shared cards, identical names, spelling variations, multiple cards: rely on stable customer IDs, not payer names. Different verified customer identities never merge on names. No verified ID => named-unverified or unknown; unresolved cannot be counted as a distinct new/returning person. Preserve source facts, name-source, confidence, conflict and freshness separately; show payer name vs customer where not demonstrably same.
3. Canonical SQL projection using existing current operational archive (not diagnostic), one check identity assignment keyed by business + restaurant + order GUID + check GUID; no fallback array index for persistent identity; missing GUID -> unresolved. One stable identity mapping per tenant and provider scope; evidence references existing archive revisions. No second ingestion, scheduler, or independent customer data store unless audit proves necessary and owner approves. Prefer recomputable views over mutable identity records; preserve prior facts by existing raw change history, last-good handling and explicit ambiguity. Use existing source completeness markers, actual/provisional, refunds/void/test exclusions. Orders may have several checks; spend/items attributed once by check, visits at most once per identity/order (not per payment or check); no attribution across conflicting IDs. Entire cafe totals reconcile including unresolved spend. Distinguish paid check net sales from gross tips/tax/tender amounts; use shared cents and official refund/discount semantics, validate including partial refunds, no duplicate tender. Define first observed vs true first visit based on available complete history; returning if prior verified eligible visit; incomplete coverage -> unknown/not established; retention cohorts with explicit denominator/window/coverage; favorite products by actual item units via canonical menu IDs, ties explicit. Frequency counts distinct eligible visits; currency/timezone from cafe settings. Owner approval for metric definitions and visit unit. Database aggregates; same canonical metrics, authorized scope and uncertainty to Supervisor and any actual UI consumers, avoid raw payload/model identity invention; no new customer screen proposed until confirmed owner UX scope.
