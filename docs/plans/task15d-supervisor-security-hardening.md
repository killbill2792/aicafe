## Threat model and proposed behavior
Attacker controls email From/Reply-To-like text, subjects, bodies, threaded quotes, documents, filenames, cells/formulas (including hidden content), PDFs/images, external results/URLs, strings in tool outputs or saved summaries; can request secrets, fake owner approvals/system roles, switch cafe/IDs, inject links or tool JSON, create false receipts, induce new purchase/price/email or poison memory/mandates, repeat or race revocation (including revoke+regrant/account swap, membership removal and process restart), manipulate approved draft and cause confused-deputy use of allowed tools. Compromised authenticated owner session, compromised provider, malicious application deploy, and already-transmitted network bytes cannot be fully solved here; no endpoint for arbitrary browser login/click, external payment, or new connector. Fail closed on unknown role, source scope, permission read, revision, or receipt; preserve independent safe work and clearly report incomplete evidence.

One registered Supervisor continues useful investigations using canonical tools. Server marks source trust independently of model, not a keyword firewall. Treat all external body/header/URL/file content and derived summaries as data, not trusted control-plane text; never convert to authentic owner statement/permission. Use existing owner-authenticated transport (web/verified WhatsApp) and membership/thread scope; sender display name or matching email address is not authenticated owner identity. Supplier/staff identity claims may be compared only against existing cafe-scoped canonical contacts and verified source records, ambiguous/unverified identity remains a claim, no contact update or effect on assertion alone. Confirm via established channel, not a link/address supplied by attacker. Preserve existing exact click/mandate rules and the narrow existing explicit-inventory owner statement path; quotes/negation/unrelated uploaded content never grant it. Off-turn work carries actual service-origin intent not a fabricated owner message. A useful inert, explicitly scoped proposal can be generated in a legitimate delegated workflow; never treat an unexpected external instruction as delegation, never auto-submit approval, never expand recipient/amount/action beyond authenticated approval. Existing approval UI shows exact recipient including CC/BCC, subject, body, material fields and source uncertainty; test existing behavior first.

### Outbound confidentiality decision (recommended)
Public web permission is not permission to disclose private cafe data. Replace arbitrary model-authored outbound query in private-evidence contexts with a deterministic constrained projection: only explicit owner-designated public search terms/current owner-supplied valid public page and bounded server-derived public facts/approved public research templates (city/date/category/event/weather etc. from existing event context). Validate at server transport; do not forward free-text mixed with mailbox/document/private tool content, don't use arbitrary URL/query parameters from external sources, reject encoded/obfuscated/unbounded variants and credentials. If no safe independently public projection, ask owner for public search terms or continue local investigation. Preserve ordinary legitimate public searches and scheduled event paths; verify the exact contract and privacy boundary for every reachable transport. No general claim that arbitrary strings can be perfectly classified or semantic leakage completely detected. Never forward tools' private records to search or third parties just because requested by external text. Authenticated, explicitly approved Gmail communications remain allowed through existing exact-payload gateway, not blanket deny. Prevent raw provider tokens, credentials and private fixture canaries in logs/diagnostics and wrong-cafe UI/exports. Do not send external URLs with private parameters or fetch internal endpoints; retain existing public page restriction.

### Data and authority contract (no new table, default plan)
Existing source records and keys:
- Gmail: connector account ID, provider subject and generation + business/owner, message/thread/attachment provider IDs, source time, header/body/labels are evidence; bind returned source to read operation, scope, generation. No body/credential duplication; provider credentials remain encrypted server-only. A provider ID proves mailbox object, not sender truth.
- Files: existing ai_attachments record (business_id, owner_user_id, thread_id, attachment UUID, MIME, content hash/time) plus existing file_read and attachment permission revisions; file filename/text/PDF/image/cells untrusted. Never execute formulas, macros or active markup; preserve bounded original content.
- Web: existing public_web permission resource and revision, owner/cafe, canonical public query/page, cited URL and observed timestamp; no credentials, raw search payload, new crawler or stored arbitrary private content. Existing city facts remain canonical, not a permission grant.
- Owner: existing authenticated membership/thread/ai_messages identity and channel provenance; current owner text distinct from quoted content and model results. Existing proposals, exact capability/revision/approved payload, mandates and attempts/receipts unchanged. Existing durable run/step/lease and source claims supply resume binding.
- Source/reference metadata stays in existing ai_messages grounding / existing bounded in-memory context and existing work/receipt metadata where already appropriate. Add typed versioned scope/source identifiers and revision stamps only where necessary; no raw evidence log, new permission table or parallel source cache. Prior external-derived assistant prose and numeric evidence are not fresh facts; stale/unknown provenance fail closed for future model/effect reuse, not destructive deletion of prior owner-visible history or already committed business records. Legacy unclassified history treated conservatively, not promoted to authority. If schema/RPC change or additional data retention becomes essential, obtain separate exact approval before touching it.
- Reads recheck immediately before transport and after GET/result aggregation, model context admission and before publication/next model/tool use. Track source references encountered this turn and revalidate current owner/entitlement, account identity/generation/operation, file/global/attachment revision and web revision. If a permission changes while running, discard affected fresh/streamed derived content from subsequent model/tool/publication, stop affected work, record safe reason; do not claim already-delivered content can be recalled. Verify revoke/regrant needs fresh evidence, no old authorization revival.
- Writes: exact owner/cafe/action/revision and current permissions through existing gateway + source/contact revalidation immediately before effect, DB-local changes atomic with existing CAS/locks. Do not hold DB transaction across remote call. Before dispatch revocation blocks; after dispatch external request may be irreversible, preserve pending/unknown/actual receipt and use authorized read-only reconciliation if still allowed, never blind retry or claim no effect. Distinguish revoked vs read unavailable (bounded retry, no effect). A replacement worker reads live authorization/lease and revalidates dependent evidence, never reuse stale draft, previous yes, spent mandate or cached grant. Only restart/replan with fresh evidence and valid current approval; no unauthorized owner-directed side effects or duplicated sends.
- Across cafes: scope all DB reads and IDs to authenticated business/owner/thread; service role explicit predicates, RLS/RPC negatives, per-run context not module global, no cross-cafe cached or same-ID object mix, concurrent tests. Verified data already written remains historical accurate; don't delete records on revoke.
