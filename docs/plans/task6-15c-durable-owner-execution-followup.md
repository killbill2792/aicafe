## Proposed design (one agent, one scheduler, no new queue)
1. Authenticated chat persists owner message with stable client/message identity and immutable selected input references before durable admission. Reuse supervisor_runs, supervisor_run_steps, ai_agent_jobs, ai_messages, current canonical runner and gateway. Prefer same durable admission for effect-capable owner work; no keyword/model intent router, no browser-controlled identities. Fast chat can opportunistically execute the SAME fenced admitted unit streaming status, not an independent second execution. If durable admission unavailable, expose truthful retryable admission failure, no silent unsafe inline fallback. Preserve prior canonical response, streaming, follow-up ordering, inbox consumption receipts, owner/thread and WhatsApp provenance.
2. Reuse refresh-derived's existing authorized invocation, not a second timer; gated bounded owner-run slice via same existing SQL fair selector/worker invoked separately from per-café refresh and routine work. Design deadline reservation so large refresh cannot starve owner runs or investigations; isolate failure, return sanitized counts. Existing manual endpoint remains gated and only invokes same claims. No vercel.json schedule edits. Gate default off and never enable production in this PR. Confirm actual scheduler/feature flag, capacity and current schema with separate read-only deployment audit before any release decision. Production activation is a separate owner-approved change.
3. Extend existing run-step storage and CAS RPCs to yield/checkpoint safe logical boundaries: immutable scoped intent, model-selected tool ID/version and bounded validated input refs, completed tool/operation receipt ref, checkpoint sequence/version, lease/attempt, next eligible retry and terminal reason. Persist only minimum resumable structured state, not unbounded raw prompts/reasoning/provider payloads. Existing references to source versions/hashes and canonical outputs only; re-read current source/authorization before each effect. Existing canonical job remains linked; after restart resume same run/step and continue from last verified receipt, not repeat finished work. Preserve old fixed-plan runs with explicit compatible version; no blind conversion/replay of old unknown steps. Finer checkpoint schema/SQL exact design must be reviewed before any implementation; no new table by default.
4. Retry read-only/pre-dispatch proven-no-effect failures with bounded exponential backoff + jitter, cumulative deadline/attempt/provider cost and tool cap. Independent readback for lost acknowledgement after side-effect; only exact idempotency key/revision and trusted replay contract allow retry, otherwise persist uncertain/blocked and request owner decision only if needed. Canonical grounded reply is not proof of external effect. No fabricated supplier acceptance, messaging or payment. Resume after verified outcome using existing task/investigation follow-up paths; approval waiting is persisted and not spinning model calls. Revalidate café/owner/thread, current source permissions, attachment/connector revisions, mandate and approval scope, cancellation and remaining quota before each checkpoint, provider call, and effect. Do not refund unknown consumption. Ensure stale worker cannot commit after lease replacement/cancel. Distinguish temporary auth/DB/provider unavailability from definitive access removal.
5. Reuse Task15C fleet fair selection and bounded slices; verify owner/café concurrency and same-thread ordering, poison entry recovery, no starvation as new jobs arrive. Use Work drawer canonical projection: queued, running, retry/backoff, waiting approval, blocked, uncertain, verified, cancelled; original thread, next retry/last checkpoint and actual receipts where safe, notification dedup via existing operating_tasks/ai_messages. No new UI dashboard or autonomous direct write privilege.

## Source and data contract (proposed; no migration now)
- Authenticated chat input: threadId + original clientMessageId + text + locale + selected attachmentIds. From trusted registration derive message UUID, owner, café, exact thread, channel/provenance. Scope and revisions validated against ai_messages/ai_attachments/current memberships; store immutable authorized reference set and locale, not uploaded bytes or secrets. Duplicate client ID returns same intent and rejects changed payload. Files remain in existing scoped store; never infer attachment from another turn.
- supervisor_runs: unique scoped request key = original owner message UUID, linked job/run/plan version and status; existing run ID retained across recovery. supervisor_run_steps: run ID + stable step key/sequence, CAS token/expiry, attempt, next retry, completed receipt ref, error class. Extend existing records only as needed; no duplicate queue, no arbitrary caller-supplied plan.
- ai_agent_jobs: per owner-message job with thread ordering and inbox; fence job ownership, durable absorbed IDs and finish/ref handoff in same recovery contract. Existing canonical ai_messages reply ID and effect gateway receipt IDs are separate outcomes.
- Existing supervisor_proposals/effect attempts: exact hash, revision, authorization and provider receipt; never grant new authority in checkpoint. Existing usage ledger: reservation per actual transport attempt with owner/thread/run/step/job/lease; missing ack remains consumed/conservative. Existing routines/investigations/commitments: schedule/episode/occurrence identity unchanged. Different cafés have distinct membership, data, timezone, entitlement, permissions, cap and evidence; no hardcoded business values.
- Only service-role scoped writes; owner reads existing RLS/projection. No raw model reasoning, credentials, sensitive diagnostics or duplicate source documents. Define retention and bounded checkpoint size before migration.
