## Proposed product and data architecture
One verified public occurrence, existing city_events UUID and city_event_sources, existing cafe_events association and cafe_event links tenant scoped; no separate event DB or daily duplicate event records. Existing legacy event ID remains stable or reversible alias, never remap by name alone. Public input: trusted provider occurrence ID/source URL + organizer identity when present; title, kind, venue/address and coordinates if actually known, start/end dates, start/end local times, source timezone/offset and confidence, date precision (single verified day vs uncertain end), attendance evidence by day vs aggregate, verification timestamps/status and explicit source changes. No guessed duration, distance, attendance, schedule, staffing or stock. Source gaps separately described; unknown facts stay unknown. Retain last verified facts while recheck pending; only cited correction may shorten/extend/reschedule; explicit cancellation ends active demand, preserves history; reinstatement reuses ID if verified same occurrence; distinct recurring editions remain distinct. Map source timezone to cafe-local business dates exactly; date-only inclusive ranges (Nov 17–19); timed intervals half-open at exact midnight, explicitly overnight, DST and timezone changes. Unknown end: mark uncertain, never invent infinite recurrence or silently assert completed. Cross-city shared public facts never expose private cafe data.
 
Canonical reader projects bounded event-day rows, not DB event duplicates. Derive upcoming/starting today/ongoing/ending today/completed (single day explicit today) against cafe-local date and verified timing, separate cancellation/moved/verification pending. Show in Home, Now/Upcoming/Past, calendar (each applicable visible date), detail (selected date plus whole interval), and Supervisor using same identity and facts. Separate sticky relevant event visibility from daily assessment outcome: previously high priority with unknown later day remains visible as "assessment pending", not guaranteed demand; verified day-level low relevance/closed hours is explicit, not hidden silently. Confirm with owner whether ongoing event appears in Past's historical day slices while its overall state remains ongoing (recommend yes). City catalogue remains one record per occurrence; date views expand only as needed.

Keep existing scheduled lookahead and today-live cron, event_readiness registered capability, supervisor proposals/monitor samples/reports, operating_tasks, ai_messages, notifyOwner and approval machinery. One event-level readiness context/thread/approval for unchanged actions, keyed by tenant + owner + stable occurrence/effect revision; day assessments scoped to occurrence + cafe date with source/evidence version, durable no-action/unknown/assessed using existing event assessment task/proposal payloads (do not introduce a new ledger). Existing legacy date-key records remain readable; avoid double-notice or double-monitor while migrating semantics. Multiple simultaneous events remain separate facts; cafe-day sales totals counted once, not attributed to every event. Shared preparation actions grouped; altered effect needs only a new exact approval when required, not auto-executed. Daily prep considers distance, verified per-day opening/event hours and attendance/source coverage, comparable historical sales, staff availability and inventory as available. Public research reused across event days; only material missing/change evidence triggers bounded permission-checked calls. Evidence hashes include meaningful source/day/evidence changes, exclude timestamps that change without content. No re-approval merely because date rolls over, no false no-action on missing evidence; retry limited/fairly across cafes and dates. Monitor provisional live actuals during opening hours, reconcile certified end-day and corrections; daily and cumulative report over unique date samples, clear provisional vs actual/estimate/incomplete, no causal attribution; preserve previous owner decision, explicit cancellation or materially changed preparation triggers a single reviewed update. Existing capability remains sole writer, including overlaps; no new cron, independent agent, parallel event database or provider. >14-day events visible; use bounded existing monitor windows and roll forward without losing prior reports, subject to explicit design approval (do not silently expand limits). No actual staff/inventory/purchase/price/external effects without exact owner approval and verified existing effect receipt.
