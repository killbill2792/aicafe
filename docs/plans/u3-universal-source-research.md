## 1. Product principle
AI Cafe is an AI system that uses traditional software to accomplish objectives, not a traditional system that asks AI to execute known question templates. Define **data, meaning, identity, authorization and correctness once**. Luna chooses objectives, research strategy, sources, queries, hypotheses, comparisons, sufficient evidence, limitations and communication. No per-question router, hardcoded query recipes, mandatory discovery sequence, fixed corroborating tool count, new persona, second agent, or separate source archive. An unknown business question is a valid use case; an unavailable fact is an honest gap, not an invented answer. Canonical means a consistent meaning and shared source of truth, not a single giant flattened view or a limit on which questions can be asked.

## 2. Actual evidence and missing pieces (read-only)
Catalog metadata of the existing Supabase project: **221 public ordinary tables, all with RLS enabled; 2,486 physical table columns; 30 views, of which 22 are the current cv_* research interface**. RLS enabled is not proof of effective tenant/column protection. No business-record payload read or changed. These counts are a dated baseline, NOT a hardcoded future limit.

Correct financial definitions, exclusions and identity must remain executable semantics; instructions about the next tool/sequence are not data contracts. - Existing cv_orders: order_ref, guest_count, source_channel, dining_option and integer-cent net sales. - ai_toast_fields no longer samples 30 rows, contrary to stale notes. It recursively walks toast_records_for(business,null,null) over current retained data, depth <16 and array indexes through 999, groups non-null scalar leaves and reports min(jsonb_typeof(v)). Null-only paths, mixed types, literal punctuation keys, deeper paths, other array positions, earlier historical fields and pagination are missing or limited. - toast_raw_records retains current objects (business_id, restaurant_guid, entity, entity_guid and business_date where applicable; order unique index includes restaurant/date/GUID). Writers toast_archive_order and toast_archive_stage_snapshot store actual arrays of {path,before,after}; change index (business_id,entity,entity_guid,changed_at). Both tables RLS enabled with no direct anon/authenticated SELECT. Keep existing archive identity and writers; no duplicate raw history, no raw table grant. Further inspect path encoding and null/absence semantics before claiming reconstruction. Changes reflect observed changes, not guaranteed real-world effective times or a complete history.
- Current security path: browser uses RLS; agentRunner.server.ts 178–182 uses a server-owned external admin client for verified external work, canonicalData at 287 passes db + businessId. investigation.server.ts 364 passes db + businessId + aggregateOnly:true. Active toast_records_allowed definer returns owner check for authenticated role, otherwise permits privileged calls. Existing app binding is not independent DB tenant enforcement for general model-authored joins/SQL. This is an expansion risk, not a demonstrated cross-café exploit. New generalized read path must enforce owner/café/lease and privacy at execution, including background work. Never forward the current admin client to a free-form query engine or forge a user session.
- Current calculate tool accepts a small arithmetic language and resolves a previous result by tool name (latest matching invocation), with units inferred from final path; typed numeric strings can be rejected. For multiple independent research queries, use exact evidence receipt/invocation/row/path plus typed unit/scale and requested period, not ambiguous latest call or JS floating point for money. Extend the existing calculator or use safe DB expressions for data aggregation; no second calculator or redefining official screen metrics.
- Source/field policy requires more than regex secret-name filtering: retain existing filtered JSON, but audit normalized path grammar, nested values, parent-object selection, aliases, grouping/filter/sort/joins and history before/after leaks. The active safe-retained JSON routine recurses with depth cap, normalizes hyphens for path admissibility; current path grammar uses dotted names with fixed depth and array index limits. Avoid loss by typed segment paths (literal key versus array index) and bounded traversal; never relax sensitive-field policy. Official schema field definitions never establish grant or observed values.

## 3. Research informing the design
- [Supabase MCP documentation](https://supabase.com/docs/guides/ai-tools/mcp): database metadata and SQL let a developer assistant explore without a developer-written question catalog. Its developer permissions are explicitly unsuitable for direct end-user exposure. Project scoping/read-only alone do not implement restaurant/owner isolation within our multi-tenant project.
- [PostgreSQL 17 row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [transaction modes](https://www.postgresql.org/docs/17/sql-set-transaction.html), [resource limits](https://www.postgresql.org/docs/17/runtime-config-client.html), [JSON functions](https://www.postgresql.org/docs/17/functions-json.html): use database-native query capabilities and layered isolation, read-only transactions, resource control and typed paths. Table owners/BYPASSRLS can evade row security; SELECT is not itself a safety proof. JSON path semantics must be explicit.
- [dbt MetricFlow semantic models](https://docs.getdbt.com/docs/build/semantic-models), [join logic](https://docs.getdbt.com/docs/build/join-logic) and [Snowflake semantic views](https://docs.snowflake.com/en/user-guide/views-semantic/overview): define entities, grain, measures, dimensions and relationships once; construct analytical combinations at research time; guard fanout/chasm joins. Adopt the principle using existing code, not another warehouse/service or independently defined metrics.
- [Spider 2.0, ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/46c10f6c8ea5aa6f267bcdabcb123f97-Abstract-Conference.html): realistic enterprise research needs metadata, project semantics, multiple queries and dialect understanding; text-to-SQL capability alone does not ensure accuracy. Published model scores are historical, not Luna performance evidence.
- [OpenAI tool search](https://developers.openai.com/api/docs/guides/tools-tool-search), [function calling](https://developers.openai.com/api/docs/guides/function-calling) and [evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices); [property-based testing](https://fast-check.dev/docs/introduction/): retrieve relevant schema/tools as needed, test properties and held-out combinations, not memorized answers or model-as-judge. Existing U2 native tool discovery and receipts are the transport; no new model router. No external package chosen yet.

## 4. Target architecture (one source graph, two existing tools)
### A. Universal source catalog, continuously checked
Extend the existing canonical dictionary into a versioned, machine-readable business catalog. Combine generated physical metadata (relations, columns/types/nullability, PK/FK, unique keys, view and function dependency lineage) with explicitly reviewed business semantics (grain, units/currency/timezone, entity and relationship identities, authoritative metric/calculator, source lifecycle, role/field/operation visibility). Use existing schema/migrations and existing business services as source; no copying operational rows into a new analytics store. Generate actual census in CI on fully migrated DB, not manually count tables. For every physical object AND field record its logical disposition: admitted authoritative detail; admitted shared metric/reference; provenance/staging/duplicate/operational infrastructure (not independent truth); restricted/secret/diagnostic; unknown/new (denied pending classification); unavailable/not retained. Include an explicit reason and source owner. Map every business domain and existing specialized read capability to logical sources; no requirement to expose physical names or all 2,486 columns to the model. Owner-visible source gaps receive a true reason and existing recovery path, not a promise. New migrations trigger catalog drift checks; changed columns are not silently exposed or silently ignored. Generate schema metadata automatically, classify once per source/field definition, not for each owner question. A newly admitted fact becomes generically discoverable/queryable without adding a new tool or scenario. Protect access to catalog metadata itself; only disclose permitted logical relations/fields, never secrets or unrelated tenant metadata.
- describe_data: search by concept/name/domain/field, exact relation, nested path or historical source; return multiple matches with semantic identifiers, units/grain, relevant relationship edges, field type set, available operation/role, provenance, as-of/coverage and bounded cursor. Model may navigate edges, expand, ask prefix/period/family, or directly query a known source. No forced sequence. Avoid vector-only or top-K discovery that hides rare fields; exact lookup, lexical and optional semantic ranking are convenience only; pagination is exhaustive for admitted scope. Use U2 deferred discovery for tool definitions; don't inject whole catalog into each prompt.
- query_data: same model-facing entry, model chooses relational operations, filters, detail, projection, join or semijoin, grouping/aggregation, derived expressions with explicit semantics, windows, distinct, sorting, comparisons, date/time intervals, history and multiple steps. Retain old schema/behavior during migration. Underlying query compiler/executor uses admitted source definitions and enforces grain, authorization and bounded workload. Known official metrics invoked through same shared source/calculator and their required filters/units; exploratory/derived metrics are explicitly named and distinguish research estimate/correlation from official totals. Provide sufficient primitives for novel analysis (including common table expressions/subqueries, per-grain preaggregation, grouping, window/rank and conditional expressions or equivalent). Avoid rebuilding all SQL as an indefinitely growing custom DSL.
- Other sources: already registered Gmail, web, uploads/documents, owner facts, previous reports and work remain their existing authorized tools/receipts. Catalog can identify their logical capabilities and permission/freshness; no raw connector credentials or unbounded ingestion into Supabase. External data is untrusted evidence, not instructions or automatic effect authorization. Luna decides which to investigate. U3 adds generic read access only to admitted stored business sources; U4 handles autonomous objective lifecycle.

### B. Decide flexible execution by evidence, not imitation of old constraints
Compare A=current single-view interface, B=governed SQL over exactly the same admitted logical sources, C=composable typed relational plan compiled into SQL (existing query_data extension). Both new candidates run on disposable migrated fixtures with identical scope, source definitions, oracle and resource budgets. Implement reusable catalog/security/admission once; comparator variants are test-only, not a second production agent. We prefer using mature SQL capabilities if a robust boundary can be independently proven, rather than recreating SQL one operation at a time. A typed compiler is preferable if it supplies equivalent general research capability with simpler assurance. **No decision made yet to permit model-authored SQL in production.** Existing SQL prohibition remains until owner approves a specific measured candidate and exact integration policy; selecting B requires explicit AGENTS/docs policy reconciliation and reviewed isolated executor design. Current plan requests comparison and common foundation, plus C implementation candidate, not deployment of unrestricted SQL.
- B must use a proper PostgreSQL dialect parser/AST, single read statement, resolve names to approved relations/functions/operators/types and safe query forms; exclude writable CTEs, mutation, locking, catalog/system access, unapproved functions/casts/operators, dynamic SQL, external IO, session/config changes, multi-statements and uncontrolled recursion/Cartesian amplification. Never regex-only SELECT filter or send model SQL to privileged RPC. Execute through tightly scoped non-owner non-BYPASSRLS role, read-only transaction, verified tenant/owner/lease supplied out of band, immutable scope that model cannot modify, private approved relation surface, fixed search_path, independently tested SQL privileges and RLS; network/sensitive catalogs unreachable as far as the admitted interface, no data write role or admin tokens. Use statement/lock timeout set before dispatch, temp/CPU/memory/concurrency/plan controls as available, real cancellation, row and byte caps, no leaked raw errors/query data. Test that constraints hold even with parser error/bypass attempts. Do not grant direct toast archive read.
- C typed inputs use closed composable primitives, not question types; validate against catalog before SQL generation and independently at execution. Identifier quoting/value binding; per-relation tenant and owner checks; safe function/operator set; type/metric/grain checks, exact row scope. Run same denial and resource tests as B. Keep advanced SQL comparator isolated, don't accidentally create parallel production read APIs. If C cannot answer expressive valid held-out queries, measure and fix capability or choose B under approval, not add a bespoke query tool per question.
- Semantic guard: enforce declared keys, cardinality, many-side preaggregation, no duplicate money through fanout, preserve observed status and denominator. No universal flat table (cartesian multiplication, synthetic identity). Correlation across same business date is not causation nor proof of employee or product attribution. Support joining at common valid grain; if no trustworthy edge exists, query separately and present limits. Model may derive hypotheses, doesn't invent facts. Same canonical metric in app/chat remains identical.
- No product-facing switch between two live engines. Final cutover one existing tool facade and shared source/evidence authority, with controlled compatibility for legacy calls. Benchmark before choosing, report capability/remaining gaps, security failures knockout. No new warehouse, dependency or connection pool without evidence and scope review. If parser dependency required, propose specific pinned version, license, security and exact package files before adding.

### C. Universal nested and historical source access
Provide scoped named scalar and structured array-element traversal (typed key/index/wildcard segments; explicit nesting grain/ordinal/GUID and spread semantics). Support mixed types, null versus key absent, bounded pagination across all authorized retained fields including rare paths and later array positions. Ordinary lookups should not walk the archive; push entity/date/path prefix into existing indexed readers, use catalog schema path patterns and exact observed metadata. Don't silently exclude depth or position; return explicit bounded continuation or capability limit, and test legal deeper/unusual keys. Prevent parent JSON, filter/group/order, discovery metadata or side-channel leakage of disallowed data. Distinguish source observed, declared but not observed, absent field, explicit null, not yet fetched, permission unknown/denied, stale/partial and read failure; only report permission denial when verified. Date fields: business event time/local business date, source observation/change time, last verified source receipt, requested/as-of period. No implicit 365-day walk; explicit historical request supported efficiently.
- Current source: existing Toast current objects and organized readers, stable keys; keep original source identity and split grain. Historic source: existing change log, original recorded path/before/after/changed_at and same business/restaurant/entity/provider ID/date. Verify actual provenance and typed absence encoding; if before/after does not distinguish missing from null, state historical ambiguity instead of inventing values. Don't reconstruct exact past state unless complete chain, baseline, effective-time semantics and source coverage verified. Historical before/after and discovery apply same recursive field/path/value policy as current data. Do not grant diagnostic/test or archive SQL directly. If ingestion loses otherwise permitted provider fields, prove source-to-storage gap and use separately approved source-owner repair; not reimport or invent missing data.
- Prefer efficient query-time metadata and existing indexes; benchmark full field walk vs prefix/exact query. Consider incremental per-source path metadata index only if need demonstrated, with metadata-only identity (cafe/source family/schema path/type/last seen) and atomic updates/backfill/coverage; exact storage/writer scope requires separate approval, no new raw archive. No unbounded scan in foreground, including no repeated full date-coverage scans or all-payload materialization.

### D. Evidence, computation, recovery and security
Every read returns source identity and logical query/receipt ID, source/metric version, requested and observed period, status/coverage/freshness, units/currency, row grain and stable provenance reference, join/aggregation denominators, counts and limits/continuation, exact reason if missing/truncated/denied. Use typed numeric values (integer cents or exact decimals; don't lose bigint/precision or silently use zero); provenance and amount association intact through paging and subsequent calculations. Extend existing calculate with exact prior invocation/result-row/path IDs and typed units, deterministic general analytical arithmetic/ratios/conversions/comparison where needed. Existing canonical metrics and calculation authority stay in one place; no duplicate formula engine. Owner input/assumption labeled; model cannot fabricate numeric operands. Preserve receipt across existing U2 history/checkpoints with no new private-data logging, no raw query/argument/body/secret in unscoped telemetry. Read multiple sources iteratively and verify meaningful data; do not label partial as complete. Use U2 resource receipts and existing durable checkpoint/run; return validated bounded chunks, explicit retry/refinement on timeout/permission changes; no new scheduler. Recheck owner membership/AI grant and same run/claim/lease at read and delivery/resume, not just turn construction. Browser, external chat, durable owner and aggregate-only unattended contexts use same policy, service credential cannot authorize more data. For aggregate-only privacy use approved semantic operations/dimensions and prevent small-group/identifier differencing, sensitive filters/order/group or inferred disallowed detail; document privacy tradeoffs and test repeated queries. Business owner access is role-scoped, not all project data. No external effect or approval change.
- Owner UX: model asks for inaccessible owner-only info only when material; explores data itself. Preserve source links/report continuity, meaningful partial status via existing UI. No additional fixed workflow or scenario required for new question.
- Security controls are generic and deterministic. Business reasoning belongs to model; data access and correctness boundaries belong to code.

## 5. Testing approach — test a research capability, not a list of questions
Preserve existing acceptance scenarios and mandatory Task17 dynamic census. Replace scenario-per-phrasing expansion with systematic **capability and invariant** tests; examples are independent test data, never runtime prompt branches.
1. **Schema/capability census:** actual migrated schema vs generated catalog, each relation/column/source/metric/role classified, every admitted field/edge reachable; newly added safe test field + relationship discoverable through existing contract with no new query handler. Block drift and unknown field admission. Verify transitive dependencies exclude diagnostics and restricted storage. Distinguish conceptual reachability, actual permitted source coverage and missing required source.
2. **Property-based, generated tests:** seeded reproducible synthetic cafés with varied order counts, nested arrays, sparse nulls, duplicates, multi-location IDs, price revisions, timezones, currency/units, staff/recipe/procurement/event facts. Generate valid/invalid query compositions from catalog, bounded random joins/filters/group/window/sorts/exact lookups, compare against independently written SQL or pure fixture oracle, not same compiler on both sides. Test reordering, ID substitutions, duplicated child row not doubling parent metric, disjoint money partition reconciles only additive measures, zero vs null, pagination concatenation equals complete result and exact role isolation, timestamp/coverage provenance. Adverse generated tests for malformed input and privileges. Save seed/minimized counterexample; fix underlying primitive not query wording. Use existing runner/seeding unless a specific new dependency approved.
3. **Security invariants:** zero admitted foreign café/location, banned fields and credential disclosure, unauthorized details including history and aggregates, write/DDL/malicious SQL, impersonation or lease bypass; no unsafe function/alias/subquery/CTE path, malicious JSON and free-text injection, attack through filters/groups/cursors/error, resource exhaustion/cancellation. Verify actual two-café DB roles, not only app mocks. All cases must pass; any violation blocks candidate. Correctness must include integer cents, exact source grain/units/coverage and canonical app parity. Unknown, refused and unsupported are separately counted, not reported as correctness passes on answerable inputs.
4. **Comparative benchmark:** identical A/B/C fixture schema, held-out generated queries and independent expected answers, no provider first. Count answerable/refused/unsupported/incorrect, exact result parity, query calls, latency p50/p95, rows scanned/returned where measurable, bytes, resources, plan/cancellation and concurrent chat/sync impact. Include unfamiliar combinations, explicit large history, rare/deep fields, candidate errors/refinement. Proposed release floor: all deterministic admitted operations correct, zero safety failures, no known canonical regressions; measured cost and latency no arbitrary claim before run; report comparative expressiveness and missing sources. No arbitrary 1,000-case target treated as proof of all possible questions.
5. **Real Luna blind holdouts:** after code and no-provider suite, independent holdout questions across domains and compositional operations with varying phrasing/data, selected/masked until run, actual registered tool, provider/source receipt, supported answer vs limitations, independent truth/numeric and security oracle, human review for recommendations/uncertainty and analysis quality. Use same model and fixture scope for variants to measure true costs/latency/quality; coordinate one consolidated owner-authorized Task17 run, reuse existing scenario runner and IDs where equivalent; no duplicate paid tests. No forced sequence, no model evaluating itself, no exact sentence/answer template. Maintain fixed historical regressions and targeted new cases for genuine primitive/source/permission defects, not every owner question. A new capability or schema change deserves a contract test; natural language variation is tested with holdouts and generated combinations. No finite suite guarantees all future questions or 100% model truth.
Map UNI-02/03/06/12 and existing Task17B/C/D to actual registered executable cases and shared coverage generator; no removal of prior obligations. U3 coding integration requires real migrations/SQL role tests, exact CI and clean Codex. Real-model acceptance/production release remain NOT_PROVEN until authorized evidence.

## 8. Implementation refinements — one generated contract, not another dictionary

Independent follow-up cross-check (2026-11-20): read-only catalog query returned 221 ordinary public tables, 221 RLS-enabled tables, 2,486 physical table columns, 30 views and 22 canonical research views, matching section 2. No records read or changed. Read current main dictionary generator, dictionary tests, registered tools and exact calculator core. The following requirements tighten sections 4–6, and avoid adding a second semantics authority.

- **Reuse the existing generator and gate.** scripts/gen-data-dictionary.mjs already transpiles dictionary.ts and emits docs/data-dictionary.md. dictionary.test.ts currently extracts columns from a fixed list of ten historical migration files using a regex, rather than inspecting the fully migrated database. This is an actual extensibility gap. Make the migrated catalog inventory authoritative for physical schema and drift; keep reviewed logical semantics in the one existing canonical catalog and make SQL admission, model discovery, generated human documentation and property-test generation consume that same versioned definition. A generated JSON inventory is a non-authoritative build artifact derived from live disposable schema, not another manually maintained allowlist. Replace or extend the existing generator/test, retain its documentation/financial/invoker safeguards, and prove new migration fields cannot drift silently. Keep generated files reproducible and free of any tenant data.
- **General query algebra, not question-specific handlers.** The candidate must demonstrate nested boolean predicates, typed scalar expressions, null handling, date bucketing/time zones, group/having, existence/semi/anti joins, per-grain preaggregation, distinct, multi-column ordering/keyset pagination, safe set operations, windows/rank/lag and bounded derived relations/subqueries, or equivalent compositions. The model selects operations and relationships; a generic validator checks types, allowed edges, grain, units, scope and resources. A schema/relationship rule is reusable across all questions; no query-purpose enums, question-pattern dispatch or mandatory tool sequence. Do not ship an indefinitely growing SQL imitation: compare the governed SQL prototype on equivalent capabilities before selecting the production interface. Count unsupported but legitimate operations as coverage misses, not passing refusals.
- **Evidence stability across multiple queries.** Expose stable per-invocation and per-result reference, typed values, exact requested/observed/as-of dates and relation/metric versions. A follow-up may intentionally compare different snapshots; do not claim all reads share one snapshot by default. Prefer one DB statement/consistent snapshot for a comparison requiring common as-of, otherwise disclose differing observations and re-read relevant facts before claiming consistency.
