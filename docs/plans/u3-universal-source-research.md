## Executed read-only baseline
Production catalog metadata checked, no business payload read. All 22 cv_* views exist and have security_invoker=true. None of their direct stored definitions references toast_raw_samples. Active ai_query_view and ai_toast_fields are invoker functions; toast_records_for is definer and checks admitted business via toast_records_allowed. None of those three active function bodies directly references diagnostics or toast_raw_changes. This is not yet transitive lineage proof.
- ai_query_view admits one view with a fixed allowlist, date bounds, typed filters/metrics, max 100 rows; current registered dataQuery.ts uses the same authenticated business and compact whole-row response. It cannot express a general safe join across canonical grains, an independent dated before/after field query, or a paginated discovery contract. Existing canonical calculations remain authoritative.
- ai_toast_fields NO LONGER samples 30 rows. It recursively walks toast_records_for(business,null,null), depth <16 and array indexes through 999, groups non-null scalar leaves, and reports min(jsonb_typeof(v)). This misses null-only fields and mixed observed types; full history walk can be expensive; no period, cursor or field-prefix pushed into SQL. TS filters prefix after retrieval and fits whole rows to 6,000 characters, but has no continuation cursor. Official schema lists are definitions, not café observations or grants.
- Active toast_records_for reads current retained orders and non-order operational archive, reconstructs split order/check/item/payment/discount/modifier/service-charge rows, protects active-import status, current nonorders' verified location mapping and permitted JSON. No change-history read. Current record keys are business_id, restaurant_guid, entity, entity_guid and business_date where applicable; for orders the unique index is business_id, restaurant_guid, business_date, entity_guid. The existing archive has scoped date/entity and GUID indexes. Do not turn source_ref or import/run ID into a provider entity key.
- toast_raw_changes columns: id, business_id, restaurant_guid, entity, entity_guid, business_date, run_id, changed_at, changes. Active toast_archive_order and toast_archive_stage_snapshot persist actual diffs as an array of {path,before,after}; current and change tables have RLS and no direct authenticated/anon SELECT. Existing change index (business_id,entity,entity_guid,changed_at). No new copy, no direct model grant to either table. Existing stage/capture provenance and last-good partial-response behavior must remain intact.
- Canonical interfaces: cv_orders has order_ref, guest_count, source_channel, dining_option, net_sales_cents; split cv_toast_records exposes record_ref/order_ref/check_ref, counts_in_sales, source_ref, status, business_date, safe data, price_cents and discount_amount_cents; customer products exposes restaurant_ref, identity_ref, visit_ref, order_ref, check_ref, product_ref and fact_kind; customer visits has restaurant_ref, identity_ref, order_ref and canonical monetary/time facts. Labor, menu, bills, inventory, analytics, owner facts and other 22 views retain their own grains, units, permissions and dates. Restaurant identity must be proven from existing sources before a join; a missing location is not a wildcard. Do not infer cashier, shift attribution, customer identity or causation from coincident dates alone.
- Read-only audit did not validate all provider grants, live field presence, nested security paths, source freshness, or complete transitive SQL lineage. These are explicit U3 proof obligations, not assumed passed.

## Proposed implementation, no separate reader
1. Extend the existing dictionary and describe_data to describe all current canonical views, field provenance, stable relationship keys, grain, allowed metrics, units, and coverage limitations. Introduce optional period, prefix, record family and bounded cursor for retained field discovery. Merge official schema declarations with exact retained path and observed type set; distinguish present-null, absent, declared-not-observed, unverified permission, stale and provider error only where backed by evidence. Distinguish current and historical observations explicitly; no live data invented from official definitions. All permitted nested paths must be reachable with explicit paginated lookups; if the current depth/index grammar blocks an actually retained permitted field, repair both the SQL and TS grammar coherently with measured limits and stable continuation. Do not implicitly enumerate an entire café archive for a specific field; push date/entity/path predicates into the existing read path. Prefer scoped existing indexes and measured paging; if a persistent derived metadata index is later necessary, first show matched fixture measurements and seek approval for its exact storage and backfill design.
2. Extend the existing query_data contract with optional validated typed multi-relation analytical shape, not a new model-facing reader. Canonical registered relation metadata supplies grain/key/cardinality/units and permitted join edges; model chooses relations, filters, projection, aggregation, grouping, sort, limit, requested dates and additional reads. Tenant identity injected solely by server, always part of relation edges. Join restaurant and provider identity when required; refuse uncertain or fanout-ambiguous joins instead of manufacturing additive sums. Support legitimate many-side aggregation using per-grain preaggregation or validated semijoins. Do not bypass the canonical metric calculators or rederive screen-authoritative totals. Existing single-view requests and no-model routing behavior remain compatible. Use strict validated structured inputs and parameterized/quoted SQL, explicit timeout/cost/rows/byte controls, deterministic pagination and precise missing/truncated/source receipts. Permit authorized detail projection and aggregation, not arbitrary SQL, writes, unregistered functions or raw whole-table output.
3. Add historical field access as a dated, explicit selection in the same read contract. Use existing change identity with exact café, restaurant, entity, entity_guid (business_date when needed), path and changed_at; project only the requested safe permitted before/after values using the existing safe-retained-data authority. Do not expose secrets through a history diff or disclose personal detail to aggregate-only service turns. Missing path vs explicit null vs absent revision remains separate; do not manufacture historic snapshots or retroactively erase changes. Keep current archive, writers, and diagnostics unmodified unless a specific proven source defect demands a separately approved repair.
4. Comparative evaluation on identical disposable migrated fixtures: A existing query path (baseline), B isolated SQL read-only comparator with restricted fixture role, validated relation/column/function allowlist, read-only transaction, explicit scope/date, statement timeout and row/byte limit, no admin access, no external/production exposure; C extended structured candidate. Use independent fixture truth and canonical screen metric parity; evaluate expressiveness on unseen cross-domain research, correct grain/money, security reject cases, latency quantiles, input/schema/result bytes and provider receipts when authorized. The comparator is test-only; raw model SQL is NOT authorized in production. Recommend typed structured path if measured coverage and parity support it. A materially different production SQL architecture requires its own owner approval.
5. Use the existing registered Supervisor and native discovery, not fixed business question sequences. Add deterministic tests plus registered executable real Luna scenario(s) or equivalent shared scenario coverage, coordinate #533/#534/#535; consolidate live acceptance with no duplicate spend. U3 read-only research can serve interactive and unattended objectives, but unattended retains aggregate-only privacy and lease checks; no effect or approval expansion. Long work resumes through U2/existing durable lifecycle; U4 handles broader proactive strategies.
