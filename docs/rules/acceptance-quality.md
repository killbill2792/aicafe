# AI CAFE — Shared real-world Supervisor acceptance protocol

## Live local capture runner (owner-approved follow-up #477)

A real-model run is **not automatically triggered** on every PR; that would spend provider credits, require private real receipts and contaminate a holdout set. The shared deterministic evaluator integrity CI runs on every code PR, while this live capture is explicitly launched by an operator in a completely disposable local environment.

**Production model contract:** Production Supervisor currently targets `gpt-6-luna` with `gpt-4.1-mini` as fallback (`lib/ai/conversations/modelConfig.ts`). For a Luna acceptance claim, explicitly set `SUPERVISOR_OPENAI_MODEL=gpt-6-luna` in the isolated app and runner; the preflight rejects missing/other values, and the runner rejects an `agent_turn_logs.model` readback other than `gpt-6-luna`. A real fallback is a **failed Luna acceptance case**, not a passing substitute. Model name logged by the backend is not external provider-native execution attestation; independent provider proof remains a separate gate. Update this contract along with a future owner-approved production model change, never silently accept a fallback.

**Required private inputs outside the Git checkout:** 50 or more independently reviewed, distinct receipt JPG/PNG/WEBP/PDF originals and at least 30 independently reviewed conversation cases. No real labeled receipts are currently included with this repository or project handoff. Do not use the AI-team portrait assets as receipts. Each private JSON manifest has `schemaVersion:1`, `suiteId`, `datasetKind:"human-labeled-holdout"`, `reviewerApproval:{reviewerId,approvedAt}`, and `cases:[...]`. Every case has `id`, `threadKey`, `category:"receipt"|"conversation"`, `actor:{businessId,ownerId}` matching one of the synthetic `TEST_CAFES`, `input:{text,assetPath,assetSha256}` (use `null` for both asset fields on text-only cases), and `expected:{outcome:"updated"|"needs_review"|"no_action",authorization:"owner_click"|"direct_authorized"|"none",approvals,writes,extracted,maxClarifications}`. `approvals` are independently labeled `{lineId:"proposal_N",sourceLineId:"line_N"}` pairs, each linked to exactly one expected stock write. `owner_click` is required when a draft must be explicitly approved, `direct_authorized` only when the owner message authorizes a verified direct save through the product's effect gateway; `none` for no stock writes. Missing or extra approval authority fails preflight.

Write labels from the actual original **before any run**, not copied from model responses. A write is `{sourceLineId,ingredient,delta,unit,costCents}`. A posted receipt line **requires** an independently labeled integer `costCents`; a pure chat-text stock addition can use `costCents:null` when the owner did not provide a price. The runner reads and checks the **saved ledger cost**, not just the proposal's extracted amount. Before committing any labeled `owner_click` effect, the runner compares the model-generated proposals to independent expected extraction labels, checks the corresponding ingredient and cost, and performs the **same authenticated owner `approve` endpoint** as the UI. Unlabeled, mismatched, or unapproved extra items cannot be auto-approved; only then does the independent read-only SQL observer verify the actual stock delta and ledger receipt. Explicit `direct_authorized` labels intentionally require no click and must independently prove the direct save., where `ingredient` is the current seeded ingredient-name slug and `unit` is a canonical base-unit scale `g_x10000`, `ml_x10000`, or `each_x10000`. `delta` is the **integer number of 1/10,000 base units**, independently calculated from the receipt and checked ingredient conversions. This preserves database `numeric(18,4)` precision; it is **not gallons**, nor does it invent a universal pack, pump or shot conversion. `extracted` contains independently expected visible line records using the evaluator's `lineId,name,quantity,unit,costCents,confidence` schema. A purchase order not delivered must have no expected writes. A correction to an earlier purchase cannot be silently represented as a second positive stock line. Each case has a unique ID; multiple consecutive turns may share the same `threadKey` to test genuine context.

**Independent extraction labels:** Name expected extracted lines `proposal_0`, `proposal_1`, etc. in the order of actual persisted proposals. Extracted `quantity` is an exact integer count of 1/10,000 original `unit`, with unit recorded as `unit_x10000` (for example, source 1.25 gal → `quantity:12500`, `unit:"gal_x10000"`). This is a private evaluator representation, not an owner-facing unit conversion; precision beyond four decimals is rejected, not rounded. The observation IDs are derived from the database ordering, never copied from the independently labeled expected lines. These ordinals are matching keys for the oracle, NOT provider-signed physical receipt-row identities. The scorer still independently checks count, name, quantity, unit, cost and confidence. A separate source-document line identity would be needed to prove physical row alignment across non-identical model batching.\n\n**Local setup:** On a disposable developer machine with Node 22, locked dependencies, Chromium, Docker and pinned Supabase CLI v2 (the same version as existing CI), generate `supabase/seed.sql` and run `supabase start` then `supabase db reset --local --yes`. **Never use `--remote`, `--linked` or a hosted Supabase URL.** Export only local `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`, local anon/service keys from `supabase status`, a budget-limited `OPENAI_API_KEY` in the shell environment, `SUPERVISOR_OPENAI_MODEL=gpt-6-luna` for both the local app and capture process, `APP_URL=http://127.0.0.1:3000`, `ACCEPTANCE_DATABASE_URL=postgres://postgres:<local-password>@127.0.0.1:54322/postgres`, `HEAD_SHA` from the exact code under test, and `AI_CAFE_LIVE_ACCEPTANCE=OWNER_APPROVED_LOCAL_ONLY`. The runner checks that `HEAD_SHA` equals the actual `git rev-parse HEAD` checkout; do not provide the SHA of a different branch, tag or merged PR. Start the real Next.js app on localhost with these variables, then run:

```bash
node evals/acceptance/live/runner.mjs \
  --labels /private/owner-reviewed-manifest.json \
  --assets /private/receipt-originals \
```

The tool refuses production/preview hosts, missing provider keys, invalid labels, wrong owners/cafés, duplicate IDs, tampered file hashes, symlink escape, receipts in source control, undersized or duplicate-only data, and overwriting evidence files. It logs only a verdict, never private receipt contents or credentials. It logs into the app's two local owners, invokes `/api/ai/threads`, private upload and `/agent` SSE, captures first useful streamed event and completion time measured from the start of the receipt upload/owner turn (including authenticated owner approval and readback), and independently reads local `pantry_stock_purchases`, `ingredients`, `supervisor_proposals` and the existing `ai_usage_events` ledger, requiring a fully completed Supervisor stream and saved reply. For independently labeled `owner_click` purchase cases, it additionally sends authenticated approval requests for precisely the matching expected proposal lines, checks committed response receipts, and includes approval latency in completion timing. A missing model usage row is a test failure; `agent_turn_logs` is not a migrated table. Observed purchases come from **new committed stock rows**, not model text; missing, duplicate or unexpected writes cause failure. Failed model turns and malformed observations remain in the **private failure report** with case IDs and controlled error codes; the runner attempts all prepared cases, counts every failure, writes a 0600 report outside Git, and returns a failing exit code. A partial-success run cannot be graded as a pass.

**Important evidence limits:** The independent before quantity is taken from scoped local SQL, and expected after is **before + owner-reviewed expected deltas**. This is a legitimate dynamic-baseline comparison, but the baseline is database-derived, not a human-authored absolute starting quantity. Proposal payloads provide a structured proxy for extracted purchase lines; a model that only chats without producing structured lines may fail extraction acceptance. Backend `ai_usage_events` independently records model call count and token usage for the authenticated owner turn. Its durable usage ID is **not** an external provider request ID, and the scorer therefore retains `objective_checks_pass_subjective_and_provenance_unverified` even on a perfect objective run. A reopened inventory screen, human wording rubric and independently captured competitor sessions require separate evaluation. Never claim those were measured because the JSON scorer returned a success status.

## What data goes where

| Input / evidence | Source | Key | Retention / authority |
|---|---|---|---|
| Test utterance, expected receipt items, units, costs and intended stock effects | Human-written/owner-reviewed case label, independently checked against an actual receipt or source | suite ID + case ID + source SHA-256 | Synthetic calibration in Git; real receipt labels are private and anonymized |
| Original receipt photograph/PDF | Owner-supplied test upload, explicit consent and redaction | SHA-256 of original bytes + test case ID | Private short-lived test storage, never in repository or public CI logs |
| Observed model text, tool calls, latency, idempotency response | Real Supervisor turn on an explicitly isolated test café | CI run ID + exact head SHA + case ID + model request ID | Redacted CI artifact; runner provides evidence, model does not label itself |
| Persisted inventory readback | Separate authenticated **scoped SQL read**, before and after effect; also verify stock screen | café + ingredient + base unit + observed time + write receipt ID | Ephemeral disposable DB; test never writes live production |
| Subjective conversational quality label | At least one owner-approved human reviewer, blinded to system under test | case ID + rubric revision + reviewer | Secure label set; human agreement/adjudication recorded |
| Comparison to Muse/Grok | Same questions/images under comparable supported permissions | run/case/model versions | Optional. If not performed, parity remains **UNPROVEN** |

**No production tables, log pipelines, auth providers, schedulers, external writes or paid inference are added by this foundation.** The only persistent repo inputs are synthetic calibration JSON; real-world observation files are passed via the acceptance CLI and never committed.

## What every code PR runs automatically

The existing required GitHub `AI CAFE PR baseline` gains one no-secret **Acceptance evaluator integrity** job. It runs the Node built-in test suite and calibration CLI on the checked-out PR head. The aggregator requires success, or requires an explicit expected skip on docs-only changes. It checks that the scorer will reject each deliberately corrupted observation: missing or skipped cases, wrong owner/café, changed receipt bytes, missing DB receipt, false stock totals, duplicate lines, fake success claims, misread item/quantity/unit, over-questioning and impossible timing.

This is **evaluator integrity only**, not real-model acceptance. The existing Promptfoo job and seeded local Playwright/database jobs remain authoritative for their own claims. Other open PRs must rebase after this foundation lands on main; adding a comment or label to an old PR cannot make an old commit have tests it never ran.

## How a real pilot must work (a separate paid/credential approval)

1. Deploy/run the **same actual Supervisor code** as the PR head against a locally migrated, disposable Supabase with two isolated seeded cafés, genuine auth, one owner, and the same registered agent tools. Use a budget-limited real provider API key stored in GitHub secrets; never paste it into chat or run against production. Existing no-provider E2 remains unchanged.
2. Build at least **50 photo/document cases and 30 multi-turn conversation cases**, independently labeled by an owner reviewer before running the model. Mix clear, crumpled, rotated, blurry, duplicate, multi-line and non-delivered documents; receipts with discounts, ambiguous pack sizes and units; corrections; wrong-café access; repeated replay and transient failure. Keep a *held-out* test split not used to tune prompts. Do not silently generate a label from the agent's prediction.
   The live scorer also requires at least 80% distinct receipt asset hashes and at least 80% distinct conversation prompts, and rejects reused provider request IDs; intentionally repeated inputs still count toward the remaining allowance. Diverse file hashes alone do not prove independent human annotation or varied visual difficulty.
3. For each case, capture the input's file SHA-256, real provider/model/request identity, first-useful-response and completed-operation time, raw tool effect receipts (redacted), **before/after stock rows from independent SQL**, and an actual reopened stock-screen observation. Capture failures and timeouts as executed failures; never drop or skip them.
4. Score objective facts using `node evals/acceptance/cli.mjs --mode live --truth <reviewed-private-labels.json> --observations <trusted-ci-capture.json>`. That mode rejects recorded/synthetic evidence, missing/duplicate cases, missing actual DB readback, unverified effects, insufficient sample size and unproven model identity. It computes p50/p95 **of observed completed duration**, not model-reported timing.
5. Validate the **human wording/interaction judge** before using it. The repository's `validate-evaluator` guidance requires distinct train/dev/held-out cases; aim for at least 50 human Pass and 50 human Fail labels to measure true-positive and true-negative detection. If no calibrated judge, have two humans resolve important conversational disputes. Objective stock changes never depend on a subjective LLM judge.
6. Compare against Muse/Grok only where the same task and permissions exist. Report completion, errors, p50/p95 latency, extraction accuracy and unnecessary questions per model and scenario, plus failure examples. Any category not independently tested must say *UNPROVEN*; do not fill a number with estimates.

## Mandatory fail-closed interpretation

- **No harmful stock writes tolerated.** Wrong business/ingredient/quantity/unit, unapproved stock increase, duplicate receipt or fabricated success is a failure regardless of how fluent the model sounds. A purchase order without received goods is not a receipt.
- **Exact money and stock evidence wins over narrative.** The oracle compares human-labeled expected stock effects with independent scoped before/after readback and durable committed receipt rows. A model saying "Done" is not a database proof. All rows relevant to the scenario must be read; empty/read failure cannot be interpreted as zero stock.
- **Use the same unit and clear provenance.** The test adapter must normalize through the existing canonical ingredient conversion before writing the observation. The scorer requires exact integer quantities in that canonical unit; it must not infer gallon/liter or pack-size conversions.
- **Source integrity and actor boundaries.** The test must hash the *original bytes* before upload; the scorer compares the recorded digest and actor against independent labels. Test another owner and another café, including after permission changes.
- **Completion is not first reply.** Measure first useful response separately from confirmed DB effect and full reply. Any slow/errored attempt counts, even if a later retry succeeds.
- **Review and correction matter.** Owner follow-up questions must be specific. An uncertain item must remain unposted, while independently valid lines may be recorded. A correction to an earlier purchase must not silently create a second positive stock entry.
- **Never self-certify:** A `status=passed` field in a model/tool payload or calibration JSON is ignored. The scorer runs its own objective checks. A JSON observation alone can be fabricated; real acceptance additionally requires a trusted, provenance-bound CI execution receipt and independent human approval.
- **A green integrity job alone never equals a real-model or competitive acceptance.** The CLI's strongest live-mode result explicitly says `objective_checks_pass_subjective_and_provenance_unverified`. Any live full-acceptance claim must separately attach trusted runner evidence, external human-label audit, timing and representative test coverage.

## Integrity and holdout maintenance

When adding a domain (inventory, Gmail, staffing, cash, menu), extend the human-labeled manifest and **introduce an incorrect observation that fails before accepting the new assertion**. Keep one independent source/ground-truth owner from the implementer. Calibrate recorded tests with positive *and* negative examples and never weaken assertions merely to obtain a green run. Any changed evaluator must rerun this mutation suite and have its owner-approved reference labels checked independently. Split/test on new inputs after model or prompt changes. Do not let a test fixture double as production seed data or expose private receipts.

**PR size review note:** This initial foundation keeps expected labels and observed readbacks as separately human-readable JSON fixtures so reviewers can compare every item and stock row. The owner-authorized `big-ok` exception is used for the larger fixture/documentation diff; it does **not** waive executable CI, coverage or review gates.

**Initial calibration:** 8 intentionally synthetic scenarios covering typed purchase, multi-line receipt, unreadable photo, undelivered purchase order, duplicate receipt, cross-café denial, correction and invoice without delivery. Their named ingredient quantities are **test-only** and not business defaults. No real receipts, human holdout, real provider, production effect or competitor timings are bundled.

## Task 17a — required automatic owner-domain regression on every code PR

The existing `AI CAFE PR baseline` now requires the **Owner journey acceptance** job for every code PR, including stacked drafts. It uses `scripts/acceptance/owner-gate.mjs` to inspect the actual Git merge-base through exact PR base/head SHAs, including moved/renamed files, and select fixed registered test files for Supervisor, inventory, staffing, Gmail, routines, memory, POS and acceptance infrastructure. Changes under unknown connector families fail classification until an explicit domain contract is added. Docs-only changes do not pay a provider or run unrelated browser tests. `workflow_dispatch` requests all registered domains and must fail if any registered test does not exist or is skipped.

The job does not trust a PR description's “tests passed” claim. It runs selected Vitest and Node tests on an exact-head candidate checkout, checks actual per-file assertions and zero failures/skips/pending/todos, writes a redacted `test-results/acceptance/owner-journey-proof.json` and verifies its SHA, selected domains and actual execution count. Any missing or failing job fails the existing required baseline aggregate. Unknown/new domains must be mapped to a real registered suite with at least one passing and one rejecting regression; a passing unrelated suite cannot substitute for that contract. The existing `scripts/e2e/targeted.mjs` still separately controls real authenticated browser proof for UI changes, and full database/other Vitest jobs remain mandatory.

**Important distinction:** this is automatic **deterministic domain regression**, not an invented successful real `gpt-6-luna` inference, supplier email, stock mutation, one-screen cross-domain conversation, or Grok/Muse benchmark.
