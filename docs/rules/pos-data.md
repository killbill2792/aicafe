### Precise data classifications and naming

| Existing object / file | Classification | Authorized purpose | Forbidden usage / current gap |
|---|---|---|---|
| `toast_raw_records` | **OPERATIONAL_CURRENT** | One latest full, permitted source payload per café/restaurant/true Toast object key; unchanged polls do not duplicate | Do not add another current-object archive or use import-run IDs as entity keys |
| `toast_raw_changes` | **OPERATIONAL_CHANGE_LOG** | Field-level `before`/`after`/`changed_at` when a real existing object changes; written with current-record update | Not a second complete snapshot or a replacement current source |
| Existing Toast staging/typed facts/employee and menu directories | **OPERATIONAL_DERIVED_OR_STAGING** | In-flight import or organized projections of the same current source; screen definitions and financial calculations remain shared | Never promote transient staging or copied screen totals to an independently authoritative raw feed |
| `toast_today_live` | **OPERATIONAL_SUMMARY** | Latest bounded same-café sales summary, provisional before final closeout | Not a separate raw order archive or definitive completed day |
| `toast_records_for`, `cv_toast_records`, `cv_*`, `ai_query_view` | **OPERATIONAL_READER** | Café-scoped, current-source-backed business facts for screens and existing `describe_data`/`query_data`/one Supervisor | Must never read diagnostic/test data; current non-order/sample-backed branches are **known defects awaiting the POS0e cutover**, not approved behavior |
| `toast_raw_samples`, `toast_raw_samples_latest`, `toast_raw_sample_leases`, `lib/pos/toast/rawSample.server.ts`, `.github/workflows/toast-diagnostic-capture-manual.yml` | **LEGACY_DIAGNOSTIC_ONLY** | API coverage audits, status/permission/error/field-shape investigation, clearly labeled historical observations | **No Supervisor answers, screen metrics, current customer/employee/stock/cash/kitchen facts, fallback after a failed operational fetch, or test-café operating truth**. | `scripts/*-integration.sql`, `*.test.*`, test-café mirror fixtures | **TEST_FIXTURE_ONLY** | Disposable DB/CI assertions, including negative proof that diagnostics have no effect | Never sent to a production business answer, silently copied into operating facts or counted as real café evidence |

**Naming rule for anything new:** use `diagnostic_` / `diag_` for investigation-only code or tables, `fixture_` / `test_` for synthetic data, and an explicit operational domain name for current production source/reader objects. New diagnostic tables/files must have a `DIAGNOSTIC_ONLY` comment and may not be wired to operational canonical views. Do **not** rename the already-deployed `toast_raw_samples` table in place or create a compatibility alias without a migration/consumer/rollback plan. Its misleading historical table name is an explicit legacy exception, **scheduled for retirement only after all dependencies are cut over and verified**. New objects must not use `raw_samples` as a synonym for an operating store.

### One path, all permitted fields

```text
Toast Standard API (each café's actual permission and response)
  -> existing Toast client and 10-minute coordinating scheduler
  -> existing authorized current-object writer
       -> toast_raw_records (one record per true provider object)
       -> toast_raw_changes (only genuine field changes)
       -> existing organized facts / financial & screen definitions
  -> existing current-source shared readers (toast_records_for / cv_* / ai_query_view)
  -> existing describe_data + query_data, specialized tools and ONE Supervisor
DIAGNOSTIC_ONLY: rawSample capture -> toast_raw_samples -> diagnostics/audit, NEVER above reader
```

**Retention:** preserve all fields Toast actually returns under the connected café's legitimate permissions, including names, employee/customer IDs, customer email/phone, loyalty relationships, orders, visits, notes, staff/labor details, menus, stock, cash and kitchen facts. Exclude full payment-card numbers/PAN, CVV/CVC, magstripe/track and reusable payment/authentication credentials and non-business security secrets. Permitted personal fields remain café/role scoped; never disclose another café's data. Treat free-text notes as untrusted **data**, never Supervisor instructions. The currently deployed `lib/pos/toast/redact.ts` removes more than this approved target; repairing the existing function is mandatory but **not yet deployed**.

**Missing values:** independent fields may be explicitly `null`, absent in a partial response, not authorized, not yet fetched, stale or unavailable because of provider failure. These states are not interchangeable. A missing customer name/ID must not block an otherwise valid order, attendance event or Supervisor answer; unknown cannot become zero. A partial response must not erase a previously verified current value, nor present it as freshly verified. Every source family records actual `last_success_at`, completeness and exception; no source family is considered current merely because the 10-minute cron fired. `modifiedStartDate`/`modifiedEndDate` are already available for Toast time-entry changes, but the current daily labor gate must be fixed in POS0b.

**On-demand access:** all retained permitted fields must be discoverable by the **existing** `describe_data` and queryable through **existing** `query_data`, including rare/optional/deeply nested/old fields and relationships by verified stable provider IDs. Do not make the model ingest entire raw tables. SQL performs bounded, café-scoped aggregation/targeted lookups; row/byte caps govern *one response*, not the underlying data access. `ai_toast_fields` currently samples 30 recent objects and 200 paths, so it is **not yet exhaustive**. Current `cv_cash`, `cv_inventory`, `cv_kitchen`, `cv_dining_options` and the non-order `toast_records_for` branch still depend on diagnostics; **do not call them live until replaced and proven**.

### Toast order durability and safe conditional menus — owner-required invariants, NOT runtime approval

- **Valid orders must survive unrelated failure.** Preserve original café/restaurant/order and line GUIDs, modifier/item details and verified amounts even when a catalog size/alias is unknown; null `menu_item_id` is preferable to invented mapping or lost sale. Keep day ingestion independent of menu fetch and post-commit relinking. Preserve existing `parseToastDayPage` per-order error isolation, safely hashed and retriable malformed-order evidence, durable staged pages, checkpoint and completed-day state; do not allow a SQL/trigger failure on one row to indefinitely block other valid orders/dates. Existing `toast_import_day` is a whole-day transaction, **not** proven database-failure isolation. Retried delivery must not create duplicate canonical orders/lines or sales.
- **Never claim incomplete as complete.** An import transaction committed, a cursor advanced, a backfill run marked `completed`, a family check succeeded, mapping resolved, a day reconciled and finance verified are **different statements**. In particular, `toast_record_day_error` may advance a failed day while incrementing `invalid_days`; a run's completed state cannot override per-day coverage or outstanding recoverable errors. Keep bounded backoff, persistent per-day/per-item retry/review, dead-letter/parked evidence with recovery, and last-good source/checkpoint. Unknown money is not zero.
- **Zero sales never removes a menu item** (even over 30+ days). No deactivation of existing items, modifiers or group relationships on empty, failed, partial, mismatched restaurant, outdated/inconsistent or unproven published snapshots. Distinguish actual provider retirement/unpublication from temporary stock, schedule, visibility and no-sales events. Preserve historic IDs, recipes, owner naming/quantities and order references; retain last-good menu and flag uncertainties.
- **Conditional full menus, one current source.** The existing 10-minute coordinator may check lightweight Toast publication metadata or authorized webhook notices but must **not** download full `/menus/v2/menus` each tick or merely because a local day changed. After saving an order, evaluate provider item/size/modifier identity against the known validated catalog. A mismatch may be legacy ambiguity rather than recent publication. Fetch only on verified change or bounded recovery, prefer **one restaurant/version-validated snapshot** reused for existing staging and canonical mapping (subject to tests), prevent repeated unchanged-version fetches, and never block orders on menu fetch/lookup failure. No new parallel ingest/store/scheduler/AI reader.
- **Independent source-family health.** For orders, time entries, menu/config and other permitted Standard families, persist `last_checked`, `last_success`, verified completeness, cursors/retry attempts and stale/permission/failure reason at their real freshness granularity. A coordinator tick is not per-family freshness. Labor uses eligible incremental change checks; menu/config uses supported change signals; order changes need authorized timely coverage plus recovery and daily reconciliation. Screens and Supervisor share exactly the same scoped `received / stored / mapped / provisional / reconciled / financially verified / incomplete / stale` definitions. No incompatible duplicate truth.

Existing import/menu readers and operational behavior cannot be removed or replaced until D3's full consumer, completeness, performance, security and rollback gate is demonstrated.
