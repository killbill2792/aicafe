## 4b. POS source authority, storage and AI access — BINDING

**Read this section before any Toast/POS, SQL view, Supervisor data-query, fixture, migration or test task.**
This is the single current operational source contract. The detailed [POS0a audit](../plans/toast-standard-api-coverage-matrix.md) tracks evidence/gaps; [POS0b–POS0f briefs](../plans/universal-supervisor-task-briefs.md) assign repairs. Older migration comments, historical test fixtures and diagnostic captures **do not supersede this rule**. A developer must identify every existing producer/consumer before proposing a replacement; a successful isolated test is not proof of production consumer wiring.

### Precise data classifications and naming

| Existing object / file | Classification | Authorized purpose | Forbidden usage / current gap |
|---|---|---|---|
| `toast_raw_records` | **OPERATIONAL_CURRENT** | One latest full, permitted source payload per café/restaurant/true Toast object key; unchanged polls do not duplicate | Do not add another current-object archive or use import-run IDs as entity keys |
| `toast_raw_changes` | **OPERATIONAL_CHANGE_LOG** | Field-level `before`/`after`/`changed_at` when a real existing object changes; written with current-record update | Not a second complete snapshot or a replacement current source |
| Existing Toast staging/typed facts/employee and menu directories | **OPERATIONAL_DERIVED_OR_STAGING** | In-flight import or organized projections of the same current source; screen definitions and financial calculations remain shared | Never promote transient staging or copied screen totals to an independently authoritative raw feed |
| `toast_today_live` | **OPERATIONAL_SUMMARY** | Latest bounded same-café sales summary, provisional before final closeout | Not a separate raw order archive or definitive completed day |
| `toast_records_for`, `cv_toast_records`, `cv_*`, `ai_query_view` | **OPERATIONAL_READER** | Café-scoped, current-source-backed business facts for screens and existing `describe_data`/`query_data`/one Supervisor | Must never read diagnostic/test data; current non-order/sample-backed branches are **known defects awaiting the POS0e cutover**, not approved behavior |
| `toast_raw_samples`, `toast_raw_samples_latest`, `toast_raw_sample_leases`, `lib/pos/toast/rawSample.server.ts`, `.github/workflows/toast-diagnostic-capture-manual.yml` | **LEGACY_DIAGNOSTIC_ONLY** | API coverage audits, status/permission/error/field-shape investigation, clearly labeled historical observations | **No Supervisor answers, screen metrics, current customer/employee/stock/cash/kitchen facts, fallback after a failed operational fetch, or test-café operating truth**. This historical table, its capture functions and current rows are retained temporarily for safe migration/cleanup; the former scheduled workflow and script were retired in PR #400, replaced by an **owner-invoked manual-only diagnostic** workflow, **not** endorsed as operating sources |
| `scripts/*-integration.sql`, `*.test.*`, test-café mirror fixtures | **TEST_FIXTURE_ONLY** | Disposable DB/CI assertions, including negative proof that diagnostics have no effect | Never sent to a production business answer, silently copied into operating facts or counted as real café evidence |
| Official Toast Standard OpenAPI schema and versioned operation/field inventory | **SCHEMA_DEFINITION**, *not observed data* | Complete field discovery and operation/permission contract, independent of sampled records | An official field need not have appeared in 30 samples; it has no observed café value until retrieved |

**Naming rule for anything new:** use `diagnostic_` / `diag_` for investigation-only code or tables, `fixture_` / `test_` for synthetic data, and an explicit operational domain name for current production source/reader objects. New diagnostic tables/files must have a `DIAGNOSTIC_ONLY` comment and may not be wired to operational canonical views. Do **not** rename the already-deployed `toast_raw_samples` table in place or create a compatibility alias without a migration/consumer/rollback plan. Its misleading historical table name is an explicit legacy exception, **scheduled for retirement only after all dependencies are cut over and verified**. New objects must not use `raw_samples` as a synonym for an operating store.

### One path, all permitted fields

```text
Toast Standard API (each café's actual permission and response)
  -> existing Toast client and 10-minute coordinating scheduler
  -> existing authorized current-object writer
       -> toast_raw_records (one record per true provider object)
       -> toast_raw_changes (only genuine field changes)
       -> existing organized facts / financial & screen definitions
  -> existing current-source shared readers (toast_records_for / cv_* / ai_query_view)
  -> existing describe_data + query_data, specialized tools and ONE Supervisor
DIAGNOSTIC_ONLY: rawSample capture -> toast_raw_samples -> diagnostics/audit, NEVER above reader
```

**Retention:** preserve all fields Toast actually returns under the connected café's legitimate permissions, including names, employee/customer IDs, customer email/phone, loyalty relationships, orders, visits, notes, staff/labor details, menus, stock, cash and kitchen facts. Exclude full payment-card numbers/PAN, CVV/CVC, magstripe/track and reusable payment/authentication credentials and non-business security secrets. Permitted personal fields remain café/role scoped; never disclose another café's data. Treat free-text notes as untrusted **data**, never Supervisor instructions. The currently deployed `lib/pos/toast/redact.ts` removes more than this approved target; repairing the existing function is mandatory but **not yet deployed**.

**Missing values:** independent fields may be explicitly `null`, absent in a partial response, not authorized, not yet fetched, stale or unavailable because of provider failure. These states are not interchangeable. A missing customer name/ID must not block an otherwise valid order, attendance event or Supervisor answer; unknown cannot become zero. A partial response must not erase a previously verified current value, nor present it as freshly verified. Every source family records actual `last_success_at`, completeness and exception; no source family is considered current merely because the 10-minute cron fired. `modifiedStartDate`/`modifiedEndDate` are already available for Toast time-entry changes, but the current daily labor gate must be fixed in POS0b.

**On-demand access:** all retained permitted fields must be discoverable by the **existing** `describe_data` and queryable through **existing** `query_data`, including rare/optional/deeply nested/old fields and relationships by verified stable provider IDs. Do not make the model ingest entire raw tables. SQL performs bounded, café-scoped aggregation/targeted lookups; row/byte caps govern *one response*, not the underlying data access. `ai_toast_fields` currently samples 30 recent objects and 200 paths, so it is **not yet exhaustive**. Current `cv_cash`, `cv_inventory`, `cv_kitchen`, `cv_dining_options` and the non-order `toast_records_for` branch still depend on diagnostics; **do not call them live until replaced and proven**.

**First-read and conflict priority:** `AGENTS.md` → this binding POS source authority → [#398 Start here](../plans/toast-standard-api-coverage-matrix.md#start-here--durable-agent-handoff-and-conflicts-index-2026-11-07) (approved D1–D4A/D4B plus current/target gaps) → [POS0 task brief](../plans/universal-supervisor-task-briefs.md) and [machine queue](../plans/universal-supervisor-queue.json) → actual code and **active** SQL → [executed tests](tests.md). `docs/README.md` reclassifies old Toast pilot guides; they and the original [Nov 3 Toast storage plan](../plans/toast-storage.md) are useful historical evidence, **not** current runtime instructions. Never claim deployed non-order readers are fixed because this design says samples are forbidden: POS0e still owns the current SQL cutover and generated `lib/data/canonical/dictionary.ts` daily-capture text under distinct approval; POS0f tests final migrated and transitive SQL lineage. The old plan's suggestion to retire `seen_run_id` **is not implemented**: live records and active `toast_archive_order` / `toast_records_for` still use it. SQL order-poison-day isolation and `liveArchive.server.ts`'s **logged-and-returned failed archive pages** (today's read can still report success) are **future separately assigned** order-recovery tasks; the 5 AM day importer is a fallback only if it later succeeds, not a justification to replace the existing importer now. Any consumer, unknown source or schema discrepancy reopens D1/D2 interpretation before a D3 replacement can be discussed.

### Owner-approved D4A and D4B — current coordinator, scoped changes, lossless recovery (NOT code authorization)

**D4A Approach B:** Retain the existing `scheduler.ts` 10-minute operational coordinator **and separate 15-minute live-orders collection**, `toast_raw_records` current objects, `toast_raw_changes` genuine revisions, same imported orders and shared screens/Supervisor. Never full re-download every Standard API each tick or rely on webhooks alone. Per family first verify restaurant, entitlement and actual modified/version/change signal **where supported**; otherwise only a justified bounded, restaurant/version/completeness-validated full snapshot. Preserve last-good value on partial/failure. Independently record last check/success, exact scope/cursor, stale/permission/error reason, true source completeness and bounded Retry-After-aware recovery. A 10-minute tick never means a complete 10-minute refresh of each API. **Later owners:** POS0b labor/roster with eligible changed time entries and correct wages; POS0c current cash/stock/kitchen collection; POS0d metadata-driven menu/config (one validated full snapshot; no deactivation on no-sales/partial); POS0e current-only canonical reader, freshness and field access; POS0f complete actual agent/screen parity. Do not permit diagnostic or Test Café mirror data as provider truth.

**D4B safe-outcome approval:** A SQL-level bad order/record must not erase unrelated valid orders, starve later dates or cause false day/financial certification. Current per-order parser does **not** isolate `toast_import_day`'s whole-day SQL transaction from cast/constraint/trigger errors; `toast_record_day_error` can advance failed-day state; `liveArchive.server.ts` may stop saving later pages after a failed archive RPC despite a successful live reading. These are **risks**, not proof of production lost sales. Preserve existing importer, original day/financial atomicity, committed good days, idempotent revisions, bounded retry and separate post-commit derivative queue; no new cron/queue/worker/reader. Exact SQL isolation, quiescence and partial-day semantics are **UNAPPROVED** and must be designed before code.

**Existing non-regression proof required:** #189 nonce fencing, staged cursors, 429 Retry-After/backoff and generation-bound `toast_rollup_refresh_jobs`; #203 first-backfill priority, global per-restaurant five historical days/tick and fairness/missed daily jobs; #264 SQL-timeout-safe redaction and payment-gap progress during stalled backfill; #297 up to five missing/incomplete/payment-gap dates per run, 1h→24h retry and no duplicate queue. Inject **99 valid plus one SQL cast/constraint/trigger-failing order** on final migrated disposable DB: preserve idempotent valid rows, park/retry error safely, continue later dates and payment gaps, no fake completed day, money/fees/tips unchanged, and replay failed live pages. Include 100+ cafés, stale lease, 429/timeouts, correct generation ACK, p50/p95 DB/API cost and rollback. **Separate cost-queue diagnostic:** live Nov 7 read-only found 77 retry-due `toast_rollup_refresh_jobs`, zero attempts, all matching daily rollups, while no sync runs were queued/running/paused. This is **not evidence of missing orders**, and no change to that queue is approved. Proposed `POS0-order-recovery` is **not a dispatchable queue task**; owner must separately approve exact file scope, SQL mechanism and PR. See [existing #398 D4 decision card](../plans/toast-standard-api-coverage-matrix.md#d4ad4b-approved-architecture-outcome--no-runtime-approval-nov-7).

**Granular D4B (newer owner clarification, [decision](https://github.com/killbill2792/aicafe/pull/398#issuecomment-6714387485)):** A failed or poisoned **record** never globally marks good order/shift/payment/menu facts unavailable. Existing `lib/data/toastDayTrust.server.ts` correctly leaves stored rows usable despite incomplete-day status; `lib/calc/toastOwnerDay.ts` correctly withholds **day-complete aggregates** until eligibility/coverage is verified. Registered Supervisor and screens must query independently verified, durably committed facts immediately with original source and as-of; mark **only the impacted question/metric** incomplete/unverified, not every fact in that café/date. Previously certified snapshots remain usable with **old as-of labels**, never silently passed off as freshly current. Sum of available orders is **not** a final total, lower bound or estimate: refunds and adjustments may decrease figures. Never fabricate unknown values, final net sales, profits or negative adjustments.

**Recovery priority means finished when feasible, not hot-looped:** reuse provider stable identity, `toast_unparsed_orders`, stage/page checkpoints, `toast_sync_runs` leases/backoff, existing missing-day repair, current `toast_raw_records`/deltas. Classify transient 429/auth/permission, per-order parse, SQL row cast/constraint/trigger, whole database outage, expired/nonmatching run, permanent unfixable source defect and lost pages independently. Use durable bounded retries and targeted retrieval only if supported, else day reconciliation; preserve live/current-day, ordinary daily and merged #203 backfill-first and #297 bounded repairs/cross-café fairness. A permanent upstream failure may remain owner-visible without freezing other work. **B1 row savepoint/transaction mechanism and priority policy are still separately unapproved.**

**Separate cost queue ACK defect (current code read):** `lib/pos/toast/rollupRetries.ts` checks the `toast_ack_rollup_refresh` RPC `error` but does not validate returned `data===true`, so `false` can be misclassified processed. The same function's generation-aware ACK must distinguish superseded job/invalid generation from successful commit; preserve independent `toast_rollup_refresh_jobs` and never reimport correct sales to clear that cost job. A separately owned cost-queue fix/verification is required and not authorized by this documentation. Owner [#400 follow-up](https://github.com/killbill2792/aicafe/pull/400#issuecomment-6714390122).

### Toast order durability and safe conditional menus — owner-required invariants, NOT runtime approval

- **Valid orders must survive unrelated failure.** Preserve original café/restaurant/order and line GUIDs, modifier/item details and verified amounts even when a catalog size/alias is unknown; null `menu_item_id` is preferable to invented mapping or lost sale. Keep day ingestion independent of menu fetch and post-commit relinking. Preserve existing `parseToastDayPage` per-order error isolation, safely hashed and retriable malformed-order evidence, durable staged pages, checkpoint and completed-day state; do not allow a SQL/trigger failure on one row to indefinitely block other valid orders/dates. Existing `toast_import_day` is a whole-day transaction, **not** proven database-failure isolation. Retried delivery must not create duplicate canonical orders/lines or sales.
- **Never claim incomplete as complete.** An import transaction committed, a cursor advanced, a backfill run marked `completed`, a family check succeeded, mapping resolved, a day reconciled and finance verified are **different statements**. In particular, `toast_record_day_error` may advance a failed day while incrementing `invalid_days`; a run's completed state cannot override per-day coverage or outstanding recoverable errors. Keep bounded backoff, persistent per-day/per-item retry/review, dead-letter/parked evidence with recovery, and last-good source/checkpoint. Unknown money is not zero.
- **Zero sales never removes a menu item** (even over 30+ days). No deactivation of existing items, modifiers or group relationships on empty, failed, partial, mismatched restaurant, outdated/inconsistent or unproven published snapshots. Distinguish actual provider retirement/unpublication from temporary stock, schedule, visibility and no-sales events. Preserve historic IDs, recipes, owner naming/quantities and order references; retain last-good menu and flag uncertainties.
- **Conditional full menus, one current source.** The existing 10-minute coordinator may check lightweight Toast publication metadata or authorized webhook notices but must **not** download full `/menus/v2/menus` each tick or merely because a local day changed. After saving an order, evaluate provider item/size/modifier identity against the known validated catalog. A mismatch may be legacy ambiguity rather than recent publication. Fetch only on verified change or bounded recovery, prefer **one restaurant/version-validated snapshot** reused for existing staging and canonical mapping (subject to tests), prevent repeated unchanged-version fetches, and never block orders on menu fetch/lookup failure. No new parallel ingest/store/scheduler/AI reader.
- **Independent source-family health.** For orders, time entries, menu/config and other permitted Standard families, persist `last_checked`, `last_success`, verified completeness, cursors/retry attempts and stale/permission/failure reason at their real freshness granularity. A coordinator tick is not per-family freshness. Labor uses eligible incremental change checks; menu/config uses supported change signals; order changes need authorized timely coverage plus recovery and daily reconciliation. Screens and Supervisor share exactly the same scoped `received / stored / mapped / provisional / reconciled / financially verified / incomplete / stale` definitions. No incompatible duplicate truth.
- **Review/authorization boundary.** PR #398 records the read-only live 563-line/7-item size-identity mismatch, affected dates and zero unparsed rows: this is **not proof of a new menu publish**, and no production corrections are approved. Existing import/menu readers and operational behavior cannot be removed or replaced until D3's full consumer, completeness, performance, security and rollback gate is demonstrated. Implementation choices, precise file/SQL ownership, tests and migrations need **separate owner authorization**; this PR adds only requirements and does not certify behavior.

### Mandatory retirement and proof contract

1. **Declare purpose before coding:** in the PR body record authoritative source, diagnostic/fixture sources, field/key identity, real source permissions, existing writer, complete reader and screen consumers, source freshness, and explicit old-path retirement. If the author cannot identify a consumer, inspect actual code rather than guessing from a file name.
2. **Cut over consumers before deletion:** add a new compatible migration that replaces final *active* SQL functions/views; migrate operational readers off `toast_raw_samples`; update code, current rules, fixtures and tests; verify the new read path on a migrated disposable DB. Keep applied migrations immutable. A stored record alone is **not** a completed integration.
3. **Delete dead code/data deliberately:** after *zero remaining active dependencies* and owner-approved retention/backups, remove obsolete diagnostic captures, test-café mirror copies and the legacy table through a separate tracked migration and post-migration verification. Do not run `DROP`/mass `DELETE` on a live café just to save disk while old views still depend on the table. Do not keep an old diagnostic view/alias that permits silent fallback.
4. **Positive and negative executable tests:** for every source field, prove API payload -> retained current object/change log -> current canonical reader -> `describe_data` -> `query_data` -> real one-agent Supervisor answer -> any applicable screen parity. Seed diagnostic-only values (e.g. fictitious cash or customer) and assert **zero effect** on those answers. Null/missing/scope/stale and wrong-café cases must also be checked.
5. **Enforce before merge:** the existing repo guard rejects **new** operational references to retired diagnostic sources; final migrated DB tests reject **all** active operational dependencies (including unchanged legacy definitions). No mocked-only, skipped or legacy-fixture-only success. A developer must not call a task `integrated_proven` until final-head CI/Codex and the full source-to-consumer proof are recorded. Production migration/deletion and real-café validation remain separate accountable gates.

**POS0 planned ownership:** POS0a audits and approves source/schema/key/reader contract; shared retention-policy and operational-reader cutover foundations repair current global defects once (one file owner each); POS0b staff/labor, POS0c cash/stock/kitchen, POS0d setup/remaining Standard source families extend the existing pipeline; POS0e completes full on-demand field discovery and query; POS0f proves every field and rejects diagnostic contamination. **Each PR must prove at least one real stored→Supervisor query per newly integrated source family**, not defer its entire reader proof to POS0f. No second subsystem.
