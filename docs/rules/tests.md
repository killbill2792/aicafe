## 9. Tests (rules that stop regressions)
- **Do not edit or delete an existing test unless the task explicitly names that behavior change.**
  The PR must list every test changed or deleted, each with a one-line reason. Any other test change
  is treated as a regression.
- If your change makes an existing test fail, assume your change is wrong first. Fix the code, or stop
  and ask. Never loosen the assertion.
- Test behavior, not source text. Tests that grep source files are allowed only to ban retired imports.
- No vacuous assertions (`>= 0`, `toBeDefined()` alone, `length >= 0`).
- Retries in tests use a new call ID for each new call, never a reused one.
- Unit tests for every tool handler and `checkNumbers`; recorded-fixture tests for the loop.
- **Golden owner questions:** a fixed set of real owner questions on fixture data with exact expected
  numbers, checked on both the chat and screen paths. A PR that changes any golden answer must say why.

### Toast order resilience / menu-preservation acceptance — future code PRs only

**Requirements, not executed test results or implementation permission.** The owner-requested POS0a investigation in `docs/plans/toast-standard-api-coverage-matrix.md` found a whole-day SQL failure-isolation risk and real legacy size-identity gaps. Existing `parseToastDayPage` per-order catch stays intact. Do not infer SQL isolation from parser tests.
2. **Recovery + idempotence:** fail during fetch, staging, page resume, day commit, reconciliation, cost refresh and post-import relink; simulate timeout, rate limit, permission loss, consecutive retries and poison day, then recover without dropping previously committed orders or losing/checkpoint-skipping valid future days. Check per-day `invalid_days`/coverage even if run state is `completed`; prove no duplicates or sales drift after reordered, modified and repeated Toast orders.
3. **Unknown item/size/modifier:** save all identity, nested selections, actual cents and orders with unresolved `menu_item_id`; do not guess size or price, do not require menu sync to import. Reproduce the verified **563 unlinked lines / seven base GUIDs / two size variants each / zero matching size modifier GUIDs** without rewriting production rows; 24 have no modifiers, 539 have other modifiers. Investigate historic mapping and aliases before any current-menu refresh.
4. **Conditional menu requests:** no full-menu request on unchanged `/menus/v2/metadata` publication or merely a day rollover; new/stale/changed published version or permitted webhook triggers **at most one validated full snapshot per actual required refresh**, supplying existing staged facts + canonical item/modifier projections consistently. Test retries, provider outages, 404/503, version changing mid-fetch and an unchanged ambiguous item without infinite re-fetch.
5. **Non-destructive catalog:** 0, 30 or more no-sale days never deactivates an item. Empty, partial, wrong restaurant, delayed publication, stale snapshot and unknown scope do not deactivate `menu_items`, `modifier_recipes` or delete `menu_item_modifier_groups`. Real authoritative retirement/unpublish, 86/out-of-stock, schedule and visibility are independently classified. Preserve owner recipes/names, historical IDs, aliases, order links and prior last-good menu.
6. **Cross-family freshness and AI/screen parity:** existing 10-minute scheduler ticks independently from last complete order/labor/menu/config checks; simulate one failed family while another progresses. Query and UI show `received`, `stored`, `mapped`, `provisional`, `financially_verified`, `failed` and `stale` honestly for the same café/date. Exercise wrong-café access denial and negative diagnostic/test-mirror contamination.
7. **Performance and rollback:** compare request count (including full menu calls), p50/p95 time, DB/transport cost, trigger/write amplification and row cardinality with the current path; rehearse safe rollback and source-to-projection reconciliation under mixed partial historical data. Tests must run on migrated **disposable** Postgres using source-shaped provider responses, current screen code and actual registered Supervisor queries; provide job URL, command, final head SHA and outcome (not skipped/mock-only or a read-only live query).

### Source-to-Supervisor acceptance and negative diagnostic tests (mandatory for POS and data-reader PRs)
- Every new/changed Toast source family must prove a real source-shaped permitted payload is retained in the one keyed current object, updated only on actual changes, independently discoverable in `describe_data`, queryable via `query_data` and answerable in a registered one-agent Supervisor turn, with applicable screen parity. Tests must exercise actual migrated disposable Postgres, not only mocks.
- **Negative authority test:** insert synthetic values into `toast_raw_samples` only, verify the live operational `cv_*` readers, `query_data` and Supervisor do **not** return them; then insert distinct values through the real current-object path and verify only those are shown. Staleness, a 403/204 or missing field must never trigger a diagnostic fallback or fabricated zero.
- Field-universe tests must include optional fields absent from 30 recent objects, fields seen >35 days ago, >200 paths, nested arrays and nullable data. Query response caps of 100 rows / ~6 KB must not limit DB-side calculations; test filtered grouping/continuation if required.
- The old `scripts/toast-db-integration.sql` and `scripts/ai-toast-records-sql-integration.sql` intentionally assert legacy diagnostic-fed operational views; their **named assertions must be updated** at the POS0e cutover. Preserve diagnostic-specific tests separately. Never keep these assertions green by leaving a forbidden source attached; never delete unrelated regression coverage.
- A passing source-code guard alone does not prove the final database lineage. POS0e/POS0f must inspect the **final definitions after all migrations** (including dependencies of `toast_records_for`, `cv_cash`, `cv_inventory`, `cv_kitchen`, `cv_dining_options`) and reject any active dependency on `toast_raw_samples` or `toast_raw_samples_latest`.
- Every PR records test name, expected value, observed value, actual executed CI job URL and final head SHA. A skipped job, mock-only test, earlier green run or test-café mirror result is NOT proof of a real-café outcome.
