## 1. Product and boundary contract

The owner talks only to the **existing Supervisor**. Supervisor delegates staffing requests to **Olivia** (typed scheduling services, not necessarily an independent LLM), coordinates any approval, and presents Olivia-attributed plans, rationale, risks, tasks, and follow-up questions in the same conversation. Alex owns pricing, Maya supplies, Leo money/operations. Reuse the same human **employees** and persisted **operating_tasks**; never create a second owner inbox.

The MVP must work for a café with **no POS, scheduling integration, worker account, bank or sales history**: owner enters staff availability and required coverage, gets a complete seven-day proposed roster or precisely reported uncovered intervals, cost and owner-hour scenarios, approves and publishes, and later requests a safe replan. POS/hourly sales and uploaded data can improve demand projections, never gate manual planning. Staff may be reported by the owner before any worker sign-in. The owner may be a schedulable person, without requiring an is_owner role flag; map the authenticated speaker to a roster person only when explicitly linked/confirmed. Legal eligibility for $0 **cash payroll cost** must be proven for a specific case; $0 is not unknown wage, salaried rate awaiting a known hours denominator, or zero economic value of owner time. Never exploit $0 workers to ignore time preferences or fatigue.

Canonical conversation intents: record_availability, temporary_exception, request_time_off, set_coverage_requirement, plan_schedule, reoptimize, request_shift_swap, ask_analysis, approve_plan, publish_plan, get_status. Examples that must be supported:
- "Ahmed Monday 9–5, only wants four hours" = available window 09:00–17:00, **maximum assigned four hours**, not eight hours on the roster.
- "Alex Monday–Friday 9–5" = five recurring windows, not one long shift.
- "Sarah this Tuesday only 8–noon" = date exception; do not overwrite every Tuesday.
- "Ahmed Wednesday 7–11 and 4–8" = two windows and an unavailable gap.
- "Alex can't work Friday; find coverage"; "Who should open/close?"; "Who can replace Sarah?"
- "I'm available 7–11 or 2–6; which saves more?"; "I prefer mornings"; "What hours should I work?" = identify the linked person or ask only if ambiguous, then compare opportunity cost, cash wages, workload and constraints separately.
- "Build next week using manual coverage"; "Keep labor cheap without understaffing."
- "I uploaded 90 days of sales; re-optimize"; "Why is Tuesday labor expensive?"; "What would four fewer Alex hours save?"

Only clarify material uncertainty (two Alexes, unresolved locale/date/AM-PM, location ambiguity, contradictory instructions, unsafe upload extraction, conflicting previously confirmed availability). Do not re-ask known availability, qualifications, coverage or hours; do not demand integrations. Never state that a shift was worked, a worker contacted/accepted, a message delivered, a plan published, a gap fixed or a cost saved without persisted proof. Incomplete coverage must be labeled **incomplete/needs owner**, never "handled." Every result identifies proposal versus completed change, person, local dates/times, plan version/status, evidence/source/freshness, modeled costs, owner hours, gaps, warnings, and exact approval or other next action.

Do not remove that prohibition silently. Obtain explicit product sign-off for the scheduling exception and amend historical product docs in a separately reviewed phase. The future feature is **owner-directed labor optimization** supporting profitability, not a standalone generic POS clone. docs/03-screens.md calls Staff primarily a cost view and requires progressive disclosure; place availability editor/review within existing Manage Staff/Staff surfaces, with primary chat entry through Supervisor. ## 3. Component design and trust boundaries

Owner / manually entered worker report → existing Supervisor interface → semantic typed intake and authoritative server-side entity/time resolution → **owner-authenticated scheduling command/proposal service** → Olivia scheduling domain → lib/scheduling/ repositories, orchestration, commands, authorization and approval → pure lib/calc/scheduling/ planner, feasibility, coverage, cost and what-if functions → lib/scheduling/ audited plan state machine → verified response/cards in Supervisor → explicit owner approve/publish → persisted published revision → durable evaluator → existing Olivia operating_tasks → existing opted-in owner-notification transport.

Olivia is responsibility/capabilities, not an unrestricted LLM. Natural-language extraction is untrusted and produces typed previewed commands. **Binding module boundary (AGENTS.md rule 3): lib/calc/scheduling/ exclusively owns pure deterministic scheduling calculations, including availability/coverage calculations, candidate generation, feasibility and constraint validation, optimization, labor costs and what-if simulations, with Vitest coverage. lib/scheduling/ owns orchestration, input schemas and source repositories, authenticated commands, persistence, authorization, approval/publish workflows and calls into lib/calc/scheduling/; it must not implement scheduling arithmetic, feasibility, cost or scenario logic.** Both layers run on the trusted server as appropriate; never let AI execute SQL, pass business_id, select a tool outside allowlist, or self-approve. Preserve runSupervisorTurn read-only business QA including unrelated price/menu/POS/money responses. Add a separately authorized schedule-command dispatcher only after reviewed schema, confirmation, idempotency, concurrency and tests exist. Existing Team rule approval must **not** confer a schedule write permission.

Requests move through: classify → parse bounded typed payload → resolve business/location/person and effective business-local dates → load precedence-aware authoritative records → validate and surface only genuine ambiguities → preview/quote with assumptions → owner-confirmed write (when applicable) → auditable reread → grounded response. Read-only scenarios never save data. Owner-provided reports for workers have attributed source worker_reported_by_owner; they are NOT authenticated acceptance. Preserve single targeted clarification as needed and explicitly distinguish attempted from completed operations.

For schedule cards in Supervisor, expose a **server-issued opaque plan ID + version** and status; display a seven-day table with local times, optional roles, paid/owner hours, wage-only/loaded cost, evidence and uncovered segments; offer edit/approve/publish only on verified authorized plan. Use existing Staff/manage-staff context for deeper review (progressive disclosure). No worker-facing chat; no second Staff data store; no automatic publish, change to POS, payroll posting or worker contact.

## 5. Planning and cost contract

**Mandatory calculation boundary:** The complete deterministic scheduling engine lives in **lib/calc/scheduling/** as pure, side-effect-free, independently Vitest-tested functions with typed, serializable inputs and outputs. This includes availability expansion, coverage calculations, candidate generation, feasibility/qualification/overlap/rest/break and other configured constraint validation, optimization/selection, labor-cost calculations, demand-derived computations, and what-if/simulation comparisons. Reuse the canonical existing **lib/calc/** wage and profit functions; do not duplicate financial formulas. **lib/scheduling/** assembles authenticated and source-aware input snapshots, orchestrates these pure functions, and owns repositories, commands, persistence, authorization, revisions, approval and publication; no scheduling calculations may be implemented there or in AI/UI code. Inputs are a versioned snapshot of business/location timezone/open hours, explicit coverage slots, people/active status/qualifications, recurring windows and date exceptions, legal rule profile, hard/soft limits, paid/unpaid breaks, pinned assignments, wage/source states and optional demand evidence. Default no-POS mode uses **owner-entered minimum coverage**, never invented hourly demand.

Hard requirements: minute-level availability, approved leave, no overlap within known business locations, qualified opener/closer, required minimum headcount and overlap, pinned/accepted commitments, configured legal rest/break/overtime/minimum-wage constraints, hard max hours, enabled staff, DST/overnight correctness. **Never sacrifice safety for low cost.** Return exact uncovered role/location/date/time slots and specific cause on infeasibility. If legal rules or wage provenance needed for safe publishing are unknown, permit clearly conditional draft/review but block unsupported compliance/cost certainty and require targeted owner/legal review for publish; never invent jurisdictional law.

Soft objective, owner-configurable priorities: lowest **cash** labor cost, hour targets/fairness/stability, fewest inconvenient split shifts, least owner time, minimal changes to published schedule, preferred periods, demand-backed service quality. Stable deterministic tie-breaks and bounded search/solver runtime within **lib/calc/scheduling/**. Pure candidate generation + feasibility validation there precede optimization; LLM may parse intent/explain but cannot create a final unchecked roster. Timeout returns a validated partial plan or explicit unsolved constraints, never a false "optimized" claim.

Cost fields (all integer cents and consistent rounding, calculated in **lib/calc/scheduling/** using canonical **lib/calc/** money functions): shift paid minutes net of unpaid breaks; supported hourly wage and salary equivalent with verified hours; separately applied legal overtime/premiums; payroll burden with status (actual/owner-confirmed/estimate/unavailable); cash wage vs loaded payroll, comparable baseline deltas, optional owner opportunity cost and owner hours (not silently counted as payroll); no double-counting taxes, timecards, shift plans or owner economic cost. Reuse docs/05-calculations.md and actual business rate source; default 0.12 is an **estimated** project default, not a jurisdictional certainty or permission to assume 3%. Missing wage ≠ zero, salary conversion pending ≠ zero. Only compute reliable labor/sales percentage with matching period, geography and sufficiently complete net-sales evidence.

Demand quality ladder: fresh complete hourly POS actuals → verified owner-uploaded hourly transactions → owner-entered peak/hour requirements → plain owner coverage requirements. Daily-only/monthly-only sales **cannot** justify precise 2 PM vs 3 PM claims. Mark missing dates, partial orders, estimated demand and stale data. Compare scenarios using identical coverage/constraint snapshots; explain every cost and service/owner-hour trade-off and unavailable figure explicitly. A cheaper substitution counts only when qualification, availability, rest and headcount all remain feasible.

## 6. Plan, approval, publishing, reconciliation

State transition: inputs unconfirmed → verified availability/coverage → deterministic proposal (draft) → reviewed proposal → owner approves a **specific plan revision** → owner explicitly publishes that same validated revision → published/archived with audit → evaluate change/new data → new proposal revision; previous published plan persists until approved replacement. Approval and publish must be separate, explicit auditable actions (could be combined only after a separately reviewed UX/security decision). Changes after publication create a new proposal with original unchanged. Recompute on source change before publish; reject stale version/hash and conflicting employee shifts. Support multiple shifts/person/day as separate assignments, complete date-range history and rollback by new revision, not by destructive edit.

**Critical compatibility bridge:** do not write draft/proposed/published assignments to timecards; those hold observed and legacy source-marked predicted payroll input. Existing materializeSchedule.ts chooses a single recurring assignment per worker/day and produces timecards through today; setWeeklySchedule can remove/recreate matching schedule-generated rows. Before PR 3 authoring, design and test a **single source of truth for published scheduling**, with precedence and canonical contribution rules. A guarded initial bridge should let old staff_schedules and their materializer serve existing cafés **until explicit opt-in**, while opted-in plan publishing reads separate versioned assignments without materializing them to timecards. If later an owner schedule contributes predicted labor cost, replace/suppress the corresponding legacy planned contribution **once** by source/date/employee and never also count it as a worked timecard. Actual POS/owner attendance wins for observed periods, with traceable discrepancies. Do not change historical actuals, recurring history or profit calculations in PR 3 without a separate specifically authorized, tested financial adjustment.

Workers: owner-entered availability is not accepted shifts. Any contacted/confirmed state requires persisted delivery/recipient consent and actual confirmation evidence. In MVP, prepare suggested owner contact wording; unavailable StaffCommunicationProvider stays unavailable. No silent notify, auto-publish or staff communication. Autonomy policies, if later requested, are versioned allowlisted owner consent with limits, audit, expiry, rollback; existing natural-language team rules alone do not grant it.

## 9. Unresolved decisions and unsafe assumptions (gates, not skipped features)

1. **Product scope:** scheduling contradicts docs/01-product.md "Don't build"; owner sign-off and eventual product-document reconciliation required.
2. **Legal/compensation:** exact jurisdiction, employee status/eligibility for $0, non-exempt/exempt status, salary conversion, premium/overtime, minor protections and break laws are not available in the current schema. **No universal compliance or known cost claim is safe** until verified rules or explicit unavailable/review gate. Consult qualified legal/payroll review before auto-publish claims.
3. **Prediction vs attendance:** old schedule materialization creates predicted timecards and weekly changes alter schedule-generated entries. Do not attach new planner directly or historical costs can silently change. PR 3 must establish deterministic precedence, non-duplication and migration-safe opt-in.
4. **Coverage/location:** locations have open_hours but not per-location timezone/jurisdiction or staffing requirements; recurring staff_schedules are business-level. Cross-business employment conflicts cannot be asserted solved without linked identity/consent.
5. **Owner identification:** there is no authoritative automatic roster person for the logged-in owner. Do not infer by display name, zero wage, or fabricated is_owner; explicit optional identity link needed.
6. **Attachment extraction:** Supervisor storage currently includes PDF/images/text up to 2 MiB, stored_unanalysed, not a trusted CSV/screenshot extractor. Parsing into authoritative availability needs a review workflow and source validation; defer if necessary, disclose unsupported type.
7. **Proactivity/notifications:** daily UTC WhatsApp existing sender is not a scheduled staffing evaluator, worker delivery is unavailable and opt-in/local quiet hours need reviewed extension. No unsolicited worker messages or false confirmation.
8. **External demand and status:** a monthly sales export cannot justify hourly allocation. Toast external scheduled shifts and actual timecards have different authority. Need provenance and complete-coverage test before scenario certainty.
9. **Multi-location optimizer scale:** pure lib/calc/scheduling/ candidate search complexity, resource budget and deterministic safe partial output must be benchmarked in PR 2; an arbitrary LLM roster cannot pass feasibility.
10. **RLS/migration ledger:** existing generic memberships policies permit member writes to staff_schedules; new scheduling write/approve needs owner-specific policy and server check. Supabase production migration ledger might not match filenames. Verify applied migrations manually; **never blind supabase db push or db reset**.
11. **UI/interaction:** strict Supervisor final schema currently requires validated grounded blocks; add schedule cards/approval only through explicit reviewed trusted new reply type/route. Do not loosen grounding or spend 5 read-tool slots on uncontrolled commands.
12. **Published shift acceptance:** publishing is an owner commitment, **not** consent by a worker or actual attendance. If no verified worker accounts, keep acknowledgment pending.
